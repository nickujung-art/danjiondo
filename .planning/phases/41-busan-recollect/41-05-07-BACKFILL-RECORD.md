## 1. 계획이 왜 실행 불가였나 — 소요시간 추정의 모집단 오류

`41-CONTEXT.md` D-05 는 지역-월당 **11.5초**를 전제로 3그룹(5·5·6개 구) 분할을 설계했다.
그 값은 내가 `ingest_runs` 의 **`molit_trade` 최근 성공 40건 중간값**에서 뽑은 것이다.

**그 40건은 전부 일배치(`molit-daily.yml`) 실행이었다.** 일배치는 당월 1개월만 조회하고
대부분의 행이 이미 존재해 dedupe 로 넘어간다 — 그래서 빠르다. 백필은 월당 수백 행을
**새로** 넣고, 행마다 `complex_id` RPC 조회 + upsert 왕복이 붙는다. **같은 이름의 작업이
아니었다.**

진짜 값은 삭제 전 `ingest_runs` 4,006행 백업에 있었다(2026-08-19 오케스트레이터 보존):

| source_id | n | 중간값 | 평균 | p90 | 누적 |
|---|---|---|---|---|---|
| `molit_trade` | 1,903 | 66.4s | **80.2s** | 159.4s | 42.4h |
| `molit_villa_trade` | 1,853 | 17.5s | **23.8s** | 52.2s | 12.3h |
| `molit_offi_trade` | 112 | 1.7s | 2.2s | 5.0s | 0.1h |

**과거 부산 전체(201607~202608)가 실제로 54.7시간 걸렸다.** 우리 범위는 201501~ 이라
12% 넓으니 약 61시간이다. 즉 D-05 의 추정은 **약 8배 과소**였고, 그룹당 1,400~1,680
지역-월은 `timeout-minutes: 300`(5시간)에 **구조적으로 들어갈 수 없었다.**

**이 결론은 이력으로도 확인된다**: `molit-backfill-once.yml` 의 직전 5회 실행이
**전부 정확히 `5h00m20s` 에 `cancelled`** 였다. 우연이 아니라 매번 한도에 걸린 것이다.
계획 단계에서 이 이력을 봤더라면 11.5초 가정을 의심했어야 했다.

## 2. 실제로 실행한 것 — 3단계 전환

### 2-1. 그룹 A 순차 (계획대로) — 취소

- Run `32318154345`, `sgg_codes=26230,26260,26320,26350,26380`, `from=201501`, `min_linked_pct=65`
- 10분간 지역-월 3건 완료(**평균 295.9초**, 부산진구 2015년), 1,996행 적재
- 이 실측으로 D-05 의 오류가 드러나 취소. **완료분은 `ingest_runs` 에 남아 `--resume` 이 보존**

### 2-2. GitHub Actions 16구 병렬 — 취소

구 1개당 job 1개로 재편성(280 지역-월/job → 한도 내). 그러나 **data.go.kr 의 러너 IP
차단**이 지배적 요인이 됐다:

- 초회 16개 중 **12개가 `exit 75`**(`EXIT_BLOCKED_RUNNER`) — 프리플라이트가 11초에 차단 감지
- 자동 재시도를 걸었으나 재시도분도 같은 확률로 차단, 같은 구가 3~4회 반복 차단
- job 이 뜰 때마다 `npm ci`(약 1분)를 다시 치르므로 **적재보다 재시작 순환에 시간을 씀**
- 50분 경과 시점 진척 **4.3%**, 16개 구 중 12개가 2% 미만, 1개(26380)는 0건
- 완주 추정 19시간+

차단률이 코드 주석의 서술("성공 확률 회당 약 2/3")과 일치했다 — **예외가 아니라 상수**다.

### 2-3. 로컬 8병렬 (최종 채택)

`scripts/busan-backfill-local.sh` — 16개 구를 8조로 나눠 로컬 프로세스 8개 병렬.

- **IP 차단 없음** (국내 IP). 5시간 job 한도 없음. `npm ci` 재시작 비용 없음
- 단지 수를 밀도 대리지표로 최대-최소를 짝지어 균형 배분
- Actions 가 적재한 192 지역-월은 `--resume` 이 건너뜀

실측 처리율: **프로세스당 3.3행/s** (전 구·전 월 균일). 병목은 CPU 가 아니라 행마다의
`complex_id` RPC + upsert **왕복 지연**이다. 8병렬 합계 약 26행/s.

## 3. 실행 중 밟은 함정 3건

**F-1. `GROUPS` 는 bash 내장 특수 변수다.** 로컬 스크립트에서 배열 이름을 `GROUPS` 로
지었더니 할당이 무시되고 루프가 실제 사용자 그룹 ID(`197121`) 하나를 돌았다.
→ **41-02 가 만든 인자 검증이 잡았다**: `--sgg 코드 형식이 올바르지 않습니다(5자리 숫자여야
함): "197121"`. 그 가드가 없었다면 `monthRange` 가 빈 배열을 돌려 **`0건 upsert` exit 0**
으로 조용히 끝났을 자리다. **Phase 41 이 막으려던 실패 유형에 오케스트레이터가 걸리고,
Phase 41 이 만든 장치가 그것을 잡은 첫 사례다.**

**F-2. 감시 스크립트의 환경변수 전달 오류.** `node -e "..." S="$VAL"` 로 썼는데 이는
환경변수가 아니라 **스크립트 인자**다. `process.env.S` 가 `undefined` 가 되어 날짜 비교가
전부 거짓 → 활성 job 수가 항상 0, **차단 감지도 죽어 자동 재시도가 20분간 멈춰 있었다.**
조용히 아무 일도 안 하면서 정상처럼 보이는 형태 — 이 Phase 가 내내 추적한 실패 모양을
감시 코드가 그대로 재현했다. 실측 대조로 발견(틀린 방식 `0` / 맞는 방식 `18`).

**F-3. 좀비 `running` 행 20건.** Actions job 을 취소하자 `ingest_runs` 에 `running` 인 채
finalize 되지 않은 행이 남았다. `cleanupStuckRuns()` 는 각 백필 **시작 시점**에만 돌므로
그 이후 생긴 좀비는 영구히 `running` 으로 남는다. 그대로 두면 나중에 "timeout" 으로
표시되는데 실제 사유는 "취소"다. 정확한 사유로 직접 정리했다
(`cancelled: GitHub Actions job 취소로 종료 (Phase 41 로컬 전환)`).
정리 후 `running` 8건 = 실제 프로세스 8개로 원장이 실제 상태와 일치.

## 4. 계획 대비 달라진 수용 기준

**"첫 dispatch 의 skip 건수가 0" → "정확히 20, 전부 `year_month ∈ {202607, 202608}`"**

`regions.is_active` 를 켠 뒤(41-01) **일배치가 먼저 돌았다**(04:00 KST). 그래서 백필 시작
시점에 그룹 A 의 202607·202608 이 이미 `success` 였고, `--resume` 이 이를 정당하게 건너뛴다.
근거와 정정 사유는 `41-05-PREFLIGHT-NOTES.md` 참조.

부수 효과로 **"스위치만 켜면 배치가 따라온다"(41-CONTEXT 의 추론)가 실측으로 증명**됐다.

**`rows_upserted` 합계 → `transactions` 실제 카운트**

수동 재시도와 감시 자동 재시도가 겹쳐 일부 구에 job 이 2개 붙었고(`gh` 가 진행 중 run 의
`workflow_dispatch` 입력을 돌려주지 않아 식별·취소 불가), `rows_upserted` 가 이중 계산된다.
데이터는 upsert 라 손상되지 않는다. 재발 방지로 워크플로에 `run-name` 을 추가했다.

**연결률 임계 65 는 여유가 0 이었다(D-07 설계 결함)**

경남 기타 실측 baseline 이 64.7% 인데 임계를 65 로 잡았다. 백필 중 실측은 60.6~62.6%
구간에서 **상승 추세**였다 — 오래된 거래일수록 현재 `complexes` 에 없는 단지가 많아 초반이
낮게 나오는 구조다. **임계를 내리지 않는다.** 미달분은 별칭 보정 필요성의 근거로 41-09 에
기록한다.
