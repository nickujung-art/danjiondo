**즐겨찾기 추가가 2026-07-15부터 16일간 불가능한 상태**를 닫는다. 이 Phase에서 유일하게

Purpose:
- **F-02** — `favorite-actions.ts:19`의 `onConflict: 'user_id,complex_id'`가 실제 제약과 어긋난다.
  실제 제약은 **부분 UNIQUE 인덱스 2개**:
  ```
  favorites_complex_favorite_unique_idx  (user_id, complex_id, site_id)                WHERE area_type_id IS NULL
  favorites_area_type_alert_unique_idx   (user_id, complex_id, area_type_id, site_id)  WHERE area_type_id IS NOT NULL
  ```
  🔴 **부분 인덱스는 ON CONFLICT 추론이 원리적으로 불가능하다.** Postgres가 부분 인덱스를 추론하려면
  INSERT 문에 인덱스 술어와 일치하는 `WHERE` 절이 있어야 하는데 **PostgREST는 그 술어를 보낼 방법이
  없다.** 따라서 `onConflict: 'user_id,complex_id,site_id'`로 "고쳐도" **여전히 실패한다** — 이건
  추정이 아니라 프로덕션 실측으로 확인된 사실이다. 컬럼 목록을 맞추는 방향의 수정은 전부 오답이다.
- 채택안: 두 부분 인덱스를 **`NULLS NOT DISTINCT` 단일 제약**으로 통합한다.
  `20260723081433`의 주석은 4컬럼 UNIQUE를 *"area_type_id가 nullable이라 NULL이 서로 다른 값으로
  취급된다"*는 이유로 기각했는데, **그 판단은 기본 NULL 시맨틱에서는 옳고**,
  `NULLS NOT DISTINCT`(PostgreSQL 15+)가 정확히 그 문제를 해결한다. 프로덕션은 **17.6**이다.
- **F-02b** — 같은 파일의 `removeFavorite`(36~40행)·`toggleFavoriteAlert`(57~61행)에 `site_id`
  필터가 없다. `favorites`의 RLS는 `auth.uid() = user_id` **단 하나**라 site 스코핑을 하지 않는다
  (실측). 즉 danjiondo에서 즐겨찾기를 해제하면 **realtrade-story의 행까지 함께 삭제된다.**

Output: 통합 인덱스 마이그레이션 1개(**구 인덱스 DROP 없음**) + `favorite-actions.ts` 3함수 수정 +
픽스처 기반 실동작 검증 스크립트 + 수정 전/후 대조.
