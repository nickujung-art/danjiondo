**판정 수단 2종 (둘 다 쓴다)**

1. **raw EXPLAIN** — `npx supabase db query --linked "explain insert into … on conflict (…) do nothing"`.
   ON CONFLICT 추론 실패는 **플래닝 단계 에러**라 EXPLAIN만으로 확정 판정이 되고 데이터는 변하지 않는다.
   오케스트레이터가 이번 조사에서 쓴 방법이다.
2. **PostgREST FK 위반 프로브** — supabase-js로 존재하지 않는 FK 값(`complex_id` = 무작위 UUID)을
   담아 upsert한다. 판정:
   - `42P10` → **BROKEN** (추론 실패, 플래너 단계)
   - `23503`(FK) 또는 `23502`(NOT NULL) → **OK** (추론 성공, 실행 단계에서 막힘)
   - 에러 없음 → 🔴 **비정상. 데이터가 쓰였다는 뜻이므로 즉시 중단·보고**
   두 에러 모두 문장 전체가 롤백되므로 **데이터가 남지 않는다.**
   PostgREST가 `onConflict` 문자열을 실제 SQL로 번역한 결과를 보는 것이라 raw EXPLAIN보다 강한 검증이다.

**`npx supabase db query --linked` 는 읽기 검증 전용이다.** DDL 적용에 쓰지 않는다
(Scope Fence 6 — DDL은 `npm run db:push`만). 출력은 JSON이며 `rows` 배열에 결과가 들어간다.
