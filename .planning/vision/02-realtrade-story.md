## 1. 배경 — 왜 이 서비스를 먼저 만드는가

- 창부레터(콘텐츠 미디어 리브랜딩)는 스코프가 커서 기획이 길어지는 중
- 이미 단지온도에 구축된 데이터·기능은 상당 부분 재사용 가능 (신규 개발 아님, UI 재설계 위주)
- 실거래가 데이터만 빠르게 출시해서 카페 회원들에게 먼저 선보이고, 콘텐츠 미디어는 후속으로 이어감
- 브랜드명에 "이야기"를 넣어 창부레터로의 계보를 의도적으로 남김 — 향후 자연스러운 업그레이드/파생 경로

## 3. 정보구조 (IA)

**하단 탭바 4개** (SOL증권의 MY홈·주식·연금상품·AI 구조 참고, 지도는 별도 탭 없이 검색 결과 내 뷰 옵션으로 통합):

1. **홈** —
   - **일일 브리핑 카드** (상단 고정): "어제 창원·김해" 거래량 + 평균 평당가(전일대비 %) + 신고가 건수. 초기엔 고정 지역(창원·김해) 기준 하나로 통일, 개인화는 후속
   - **발견 섹션**: **인기**(실시간 조회수 기준 TOP5 미리보기, 호갱노노식) / **급등락**(**최근 30일 변동률** 기준 TOP5 미리보기, 증권식 — 기존 `price_change_30d` 재사용, §10 참고) 서브탭 2개 — "더보기" 클릭 시 랭킹 탭의 해당 필터로 이동
2. **검색** — 단지 검색(자동완성) + 지도 뷰 토글. **입력 전 기본 화면**: 최근 검색어 + 인기 검색어 (마치 포털 검색창처럼)
3. **랭킹** — 거래량·평당가·신고가·**변동률**(=급등락, `price_change_30d` 기준) TOP **전체 리스트**. 필터: **기간**(1주·1개월·3개월) × **지역**(시·구 단위, 초기엔 창원 5구+김해 1개뿐이라 단순) — 단, 변동률 필터는 `price_change_30d`가 30일 고정 window라 기간 필터와 무관하게 항상 동일 계산식(§10 항목5). 홈 "발견"과 데이터 소스는 동일(인기=`view_count`, 급등락=`price_change_30d`), 범위만 다름(발견=TOP5 미리보기, 랭킹=전체) — "더보기"가 실제로 이 필터로 연결되려면 **랭킹 탭에도 변동률 정렬 옵션 신규 추가 필요**(기존 `complex_rankings`엔 없음, §9 2단계 작업 범위에 포함)
4. **즐겨찾기** — 로그인 필요, "보유"(관심 단지) 모아보기 + 조건부 알림 설정

> 보유(즐겨찾기) vs 발견(홈) 구조 분리 — 증권 앱 패턴. 커뮤니티 없이도 "발견" 탭이 재방문 명분을 만듦

**단지 상세 페이지 안에 통합** (별도 최상위 탭 아님):
- 10년 그래프·거래내역·시설
- 투자분석(갭투자·사분면) — 직접 분석 제공이 아니라 데이터 노출이라 아직 탭 분리할 변별력 없음 판단
- AI 코멘트(12개월 예측 + Groq 해설)
- 단지 비교(2~4개 비교표)
- 학군(학교알리미 진학률·순위·연락처)
- 관리비(K-apt)

## 5. 운영 범위

- **회원가입/로그인**: 완전 비로그인 열람 원칙 + 즐겨찾기만 최소 로그인 (기존 Supabase Auth 그대로 재사용)
- **어드민 콘솔**: 필요한 것만 축소 — 광고 검수, 분양 관리, 매칭 큐(데이터 오류 대응). 회원관리·카드뉴스·공인중개사 관리는 이 서비스에 없는 기능이라 불필요
- **초기 커버리지**: 창원·김해부터 오픈, 점진 확대 (백엔드는 이미 경남 22개+부산 16개 = 38개 지역 데이터 구축 완료 — 화면 노출 범위만 단계적으로 넓히면 됨)
- **지역별 SEO**: 사이트 브랜드는 지역 중립("실거래이야기" 고정), 개별 페이지 타이틀에서 지역명 노출 (예: "창원시 성산구 아파트 실거래가 | 실거래이야기") — 기존 Phase 23 한글 URL 계층 구조 그대로 재사용

### 증권앱 UX 패턴 적용
- **조건부 가격알림** (토스증권 지정가 알림 응용) → MVP 포함
- **급상승/급하락 변동률 랭킹** (절대가 아닌 %변동 정렬, 경쟁사 대비 약한 지점) → 홈 "발견" 탭 서브탭으로 반영. MVP는 기존 `price_change_30d`(30일 기준)로 스코프 조정, 전일/전주 단위 정밀 집계는 후속(§10)
- **보유(즐겨찾기) vs 발견(홈) 구조 분리** → IA에 반영 완료 (§3)
- **일일 브리핑 카드형 시황 요약** ("창원 어제 대비 거래량·가격") → 홈 상단에 배치, 세부 설계 완료(§3)

### 8-2. 광고 배치 (2026-07-14 추가)

**주의**: "증권앱처럼"이라는 비유는 UI 스타일에는 맞지만 광고엔 안 맞음 — 토스증권 같은 증권앱은 수수료 수익 모델이라 소매 사용자에게 광고를 거의 안 보여줌. 실제 참고는 **광고로 수익 내는 아실·호갱노노**가 더 정확한 벤치마킹 대상.

**리서치 핵심 발견:**
- 호갱노노: 광고(분양)는 핵심 실거래가 조회 UI에 안 섞이고 **별도 분양 탭/섹션에 완전히 격리**
- 아실: 중개사 매물광고는 단지상세 페이지 안에서 "포커스" 라벨 붙은 **별도 블록**으로 구조적 분리(오가닉 데이터와 안 섞임)
- 사용자 불쾌도: 인터스티셜/팝업(전면광고) 43% 1위, 반대로 고정 배너는 74.6% 수용도로 안전
- 표시광고법도 "누가 광고비를 냈는지" 명확한 라벨링을 요구 — 구조적 분리가 UX적으로도 법적으로도 맞는 방향

**우리 적용 결정:**
| 광고 유형 | 배치 위치 | 형태 |
|---|---|---|
| 분양광고 | 분양 전용 섹션(기본) + 단지상세 내 소규모 배너(병행) | 호갱노노식 — 핵심 조회 흐름과 분리하되 단지상세에도 소량 노출 |
| 중개사 광고(공인중개사 추천) | 단지상세 페이지 내 | 아실 "포커스 매물"식 — "광고" 라벨 붙은 별도 블록, 중개사당 노출 건수 제한 |
| 인터스티셜/팝업(전면광고) | 미사용 | **MVP는 배제, "절대금지"로 문서화하지는 않음** — 추후 수익 압박 시 재검토 여지는 남김 |

| 단계 | 범위 | 재사용 vs 신규 | 비고 |

| 0 | ✅ **완료(2026-07-15)** — 디자인시스템 기반(Pretendard·OKLCH 토큰·Tailwind 3.4), Next.js 15 스캐폴딩, Supabase 클라이언트 이식 + DB 마이그레이션(`site_id` 컬럼, `area_type_id`·`price_drop_rate_threshold` 알림 컬럼) | 100% 신규(스타일만) + 인프라 | 신규 repo 생성 완료(`nickujung-art/realtrade-story`). `site_id` 마이그레이션도 적용 완료(`supabase/migrations/20260715000001_realtrade_story_site_scoping.sql`) — 기존 광고 9건 전부 `danjiondo`로 정상 백필 확인. 공통 컴포넌트 3종(카드리스트·알약뱃지·세그먼트토글)은 1단계 진행하며 필요할 때 만드는 것으로 조정(선제작 대신) |

| 2 | 랭킹 | 거래량·평당가·신고가는 데이터 재사용, 필터 UI(기간×지역)와 **변동률 정렬 옵션**(`price_change_30d` 신규 연결, §3 참고)은 신규 | 홈의 "발견" 섹션이 이 API를 그대로 쓰므로 반드시 먼저 |
| 3 | 홈 (일일브리핑카드 + 발견 섹션) | 브리핑카드의 "전일대비 %"만 신규 집계 필요, 발견 섹션 급등락은 기존 `price_change_30d` 재사용(§10) | 랭킹 API 나온 뒤라야 발견 섹션 연결 가능 |

## 10. 리스크 점검 및 전제 수정 (2026-07-14)

기획안의 "기존 재사용" 전제들을 실제 코드베이스와 대조 검증한 결과, 5건의 실수가 발견되어 정정했다. 실행 단계에서 발견됐다면 일정에 타격이었을 사항들.

| # | 발견 | 근거 | 정정 |
|---|---|---|---|
| 1 | 동/호수 데이터 부재 | `src/services/molit.ts`의 `MolitSaleItemSchema` 등에 동/호수 필드 자체가 없음 — 국토부 공개 API는 층수(`floor`)만 제공 | §4·§8·§9에서 "동·층·호수"→"층 단위"로 스코프 축소. 동/호수는 별도 데이터소스 필요한 후속 검토 항목으로 이동 |
| 2 | 즐겨찾기·광고 테이블에 서비스 구분 컬럼 없음 | `favorites`(`20260430000005_users.sql`)·`ad_campaigns`(`20260430000007_ads.sql`) 모두 `site_id`/`app_id` 컬럼 0건 — 같은 DB 재사용 시 danjiondo와 실거래이야기의 즐겨찾기·광고가 섞여 노출됨 | `site_id` 컬럼 신규 마이그레이션으로 분리(§6, §9 0단계) — 완전 별도 프로젝트로 가지 않고 같은 DB에 컬럼만 추가하는 절충안 채택 |
| 3 | 조건부 가격알림 스키마 절반만 존재 | `favorites.price_alert_threshold`(절대가)는 있으나 전고점 대비 하락률 조건 컬럼은 없음 — §6의 "DB 마이그레이션 불필요"는 이 이유로 이미 틀린 문장이었음 | §4·§6에서 "마이그레이션 불필요" 삭제, 신규 컬럼 필요로 명시 |
| 4 | Supabase 아직 free 플랜, DB 468MB/500MB | `get_organization` 결과 `plan: "free"`, `pg_database_size` 468MB(2026-07-14 재확인) — 어제 논의한 Pro 전환이 아직 미반영, 부산 백필도 이 이유로 일시 중단 중 | **공개 런칭(§11 소프트런칭 착수) 전 Pro 활성화 재확인을 하드 게이트로 설정**. 디자인시스템·repo·마이그레이션 등 0단계 코드 작업은 용량과 무관하니 지금 시작해도 무방 |
| 5 | "급등락"(변동률 랭킹)이 §4에서 "기존 재사용"으로 잘못 표시됨 | `complex_rankings.rank_type`은 `volume/price_per_pyeong/high_price/interest` 4종뿐, 등락률 타입 없음. 유사 컬럼 `complexes.price_change_30d`는 "30일 롤링 vs 직전 30일 롤링" 비교라 기획서의 "전일·전주 대비"와 기준 자체가 다름. 흥미롭게도 §8·§9는 이미 이걸 "신규 로직"이라 인정하고 있어 §4 표와 자기모순이었음 | §4에서 "급등락"을 별도 행으로 분리, `price_change_30d`(30일 기준)로 스코프 다운 — 신규 daily/weekly diff 로직은 만들지 않고 문구를 "최근 30일 변동률"로 정직하게 표기(2주 타임라인 고려한 현실적 타협) |
| 6 | 법적 문서(개인정보처리방침·이용약관)에 "단지온도" 브랜드명 하드코딩, 사업자 정보 자체가 부실한 초안 | `src/app/legal/terms/page.tsx` 제1조에 "단지온도" 직접 하드코딩, `privacy/page.tsx`의 `CPO_NAME`·`SUPPORT_EMAIL` 기본값도 브랜드 종속(`danjiondo.com`). 상호·대표자·사업자등록번호 등 실제 사업자 정보는 애초에 문서에 없음(둘 다 "초안 — 법무 검토 전" 명시) — 이건 브랜드 분리와 무관하게 danjiondo 자체의 기존 결함 | 실거래이야기용 `terms`/`privacy` 페이지를 사이트별로 분기(환경변수 `SUPPORT_EMAIL`/`NEXT_PUBLIC_PRIVACY_CPO_NAME` 활용 + terms 제1조 문자열 분기) — 단, 사업자 정보 부실 자체는 광고 수익화하는 서비스 2개로 늘어나는 시점이라 더 미루기 어려움. §12 미정 항목에 별도 기재 |

**추가 검증(전제가 맞았던 것)**: 홈 "발견/인기" 탭이 전제하는 조회수 트래킹 인프라는 실제로 존재함 — `complexes.view_count` 컬럼 + `ViewCountTracker.tsx`/`increment_view_count` RPC가 이미 지도 "인기" 뱃지에 실사용 중. `view_count DESC LIMIT 5` 쿼리만 추가하면 되는 수준이라 신규 인프라 구축 불필요, MVP 스코프 그대로 유지.

**추가로 결정한 것 — danjiondo와의 공존 전략**: 완전 영구 병행이 아니라, **danjiondo 트래픽을 점진적으로 실거래이야기로 유도하고 danjiondo는 서서히 sunset**하는 방향으로 결정. 두 사이트가 동일한 실거래가 데이터를 계속 병행 노출하면 구글이 중복 콘텐츠로 인식해 SEO 자기잠식 위험이 있기 때문 — 실거래이야기가 안정화되면 danjiondo의 실거래가 관련 페이지부터 순차적으로 리다이렉트/noindex 전환 검토 (구체적 전환 일정·기준은 출시 후 트래픽 데이터 보고 결정, 지금은 방향만 확정).

## 11. 카페 공지 전략 (2026-07-14 추가)

**2단계 공지 — 소프트런칭 → 정식공지**

| 단계 | 시점 | 대상 | 목적 |
|---|---|---|---|
| 소프트런칭 | MVP 완성 직후, **단 Supabase Pro 활성화 재확인 후에만 착수**(§10 항목4 참고 — 2026-07-14 기준 아직 free 플랜) | 카페 운영진 + 소수 활동회원(비공개 공유 — 구체적 인원·등급 기준은 출시 임박 시 확정) | 버그·초기 반응 수집, 전체 공개 전 첫인상 리스크 최소화 |
| 정식 공지 | 소프트런칭 후 약 1주, 안정화 확인되면 | 카페 전체(20만 회원) 공지글 | 공식 런칭 알림 |

**공지 내용 원칙:**
- 실거래이야기 소개만 — **창부레터(후속 콘텐츠 미디어) 예고는 이번엔 언급하지 않음**. 두 개념을 한 번에 설명하면 메시지가 흐려짐, 창부레터는 준비되면 별도 공지로 진행
- **danjiondo의 점진적 sunset 계획은 언급하지 않음** — 회원 입장에서 지금 알 필요 없는 내부 전환 전략, 혼란만 가중. 전환이 실제로 진행될 때 필요하면 그때 별도 안내
- **이벤트/인센티브 없이 순수 정보 공지** — "순 데이터 서비스" 컨셉과 일관되게 화려한 마케팅 없이 담백하게

**안정화 판단 기준 (초안, 출시 임박 시 확정)**:
- 소프트런칭 기간 중 크리티컬 버그 0건
- 검색·단지상세·랭킹 등 핵심 플로우 정상 동작 확인

## 12. KPI / 성공 지표 (2026-07-14 추가)

## 15. 향후 업그레이드 후보 (MVP 이후, 2026-07-14 추가)

MVP 스코프가 아니라 트리거 조건이 실제로 발생했을 때 검토할 항목들. 지금 우선순위를 매기지 않음 — 아래 순서는 자연스러운 흐름일 뿐 확정 로드맵 아님.

| 후보 | 설명 | 트리거 조건 |
|---|---|---|
| 동/호수 정밀 상세 | MOLIT엔 없는 동/호수 정보를 네이버 매물 크롤링 등 별도 소스로 보강(§10 항목1) | 아실 대비 상세도 격차가 실제 이탈 사유로 확인되면 |
| 급등락 정밀화(전일·전주 diff) | 지금은 `price_change_30d`(30일 롤링)로 대체 중(§10 항목5) — 진짜 "전일 대비" 계산은 daily diff 집계 신규 필요 | "급등락" 기능 사용률이 높아 정밀도 요구가 커지면 |
| 인앱브라우저 감지 + 외부브라우저 유도 UI | 카카오톡 인앱에서 로그인 이탈이 실제 보고되면(§13) | 카카오톡 경유 트래픽·이탈률 데이터 확보 후 |
| 개인화 브리핑 카드 | 지금은 창원·김해 고정(§3) — 사용자 관심지역 기반 개인화 | 즐겨찾기 데이터가 충분히 쌓인 뒤 |
| 지역 확장(부산 화면 노출 → 전국) | 백엔드는 이미 38개 지역 구축 완료(§5) — 화면 노출만 단계적으로 열면 됨 | 창원·김해 안정화 확인 후 |
| 매물(호가) 시세 통합 | 지금은 과거 확정 실거래만 다룸 — 아실/호갱노노처럼 현재 매물 호가까지 통합하면 차별화 강화 가능하나 스코프가 큼 | 별도 기획 필요, MVP와 거리 있는 큰 확장 |
| 실시간 알림(웹훅 기반) | 지금은 "매일 아침 체크"(§4) — 진짜 실시간 알림은 국토부 API 자체가 실시간이 아니라 근본적 제약 있음 | 국토부 API 실시간성 개선되거나 대체 소스 확보 시 |
| 알림 채널 확장(카카오 알림톡 등) | 지금은 웹푸시만(§6) | 웹푸시 도달률이 낮다는 데이터 확인되면 |
| 부동산 데이터 API 공개 | 서드파티 개발자용 실거래가 API — 데이터 중심 서비스 특성상 자연스러운 확장 | 트래픽·브랜드 인지도 확보 이후 |
| 프리미엄 구독 | 광고 외 수익원 — 정밀 알림, 데이터 다운로드 등 | 광고 수익만으로 지속가능성 부족하다고 판단되면 |
| 투자점수(리치고식) | §4에서 이미 보류 — 스코어링 모델 검증 시간 필요 | MVP 데이터로 사용자 반응 확인 후 |
| 다크모드 | `03-realtrade-story-design-system.md` §9에서 미정 — OKLCH 기반이라 확장 자체는 어렵지 않음 | 사용자 요청이 실제로 들어오면 |
