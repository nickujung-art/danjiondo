## 한 줄 정의

**창원·김해 사람들이 가장 먼저 읽는 부동산 미디어**

---

## 1. 문제 — 지금 단지온도는 뭐가 문제인가

- 호갱노노 따라 기능만 붙인 "기능 집합체"가 돼버렸다
- 누구를 위한 서비스인지 불명확
- 전국 서비스 대비 기능 부족, 카페 대비 깊이 부족
- **집 살 생각 없으면 들어올 이유가 없다**

---

## 2. 방향 — 왜 로컬 미디어인가

| 자산 | 의미 |
|------|------|
| 창원부동산이야기 카페 **20만 회원** | 이미 독자가 있다 |
| 창원·김해 다루는 로컬 미디어 **경쟁자 0** | 선점 가능 |
| 호갱노노가 절대 못 만드는 **우리 동네 이야기** | 차별화 |

→ 데이터 기능은 콘텐츠 안에 녹인다. 기능 페이지가 아니라 기사 페이지로.

---

## 3. 브랜드 — "창부레터"

- **어원**: 창원부동산이야기 + 레터(뉴스레터)
- **도메인**: changbuletter.com
- **레터**라는 이름이 이메일 구독을 자연스럽게 암시
- 카페 20만 회원 → 뉴스레터 독자로 전환하는 흐름

> **제1 옵션 확정** — 이 이름 기준으로 진행

---

## 4. 타겟

| 우선순위 | 대상 | 특징 |
|---------|------|------|
| **MAIN** | 창원·김해 거주 30~50대 | 이미 내 집 있음, 카페 회원, 동네 소식 소비 |
| **MAIN** | 이 지역 처음 오는 사람 | 삼성·포스코 임직원 이전, 학군·교통 정보 필요 |
| SUB | 로컬 투자자 | 갭투자·재건축, 데이터 기반 |

## 5. 콘텐츠 4종

| 콘텐츠 | 주기 | 채널 | 역할 |
|--------|------|------|------|
| 주간 실거래가 카드뉴스 | 주 1회 | 인스타 + 카페 | 바이럴, 이미 자동화됨 |
| 기획기사 (동네 분석) | 월 2~4회 | 사이트 + 카페 | 구글 유입·신뢰도 핵심 |
| 랭킹 인포그래픽 | 주 1회 | 인스타 스토리 | 거래량·상승률 TOP 5 자동 생성 |
| 지역 가이드 | 월 1~2회 | 사이트 | 이전자 수요, 롱테일 SEO |

## 6. 사이트 구조 변경

```
기존: 단지 검색 중심
변경: 콘텐츠 피드 중심 홈 + 콘텐츠 섹션 신설

신규: 홈(재설계), 콘텐츠, 지역 가이드
유지: 단지 검색, 마이페이지
depth↓: 지도 (메인 네비에서 빠짐)
```

## 7. 유저 동선 (4단계 퍼널)

```
진입 → 랜딩 → 탐색 → 전환/락인

[인스타·카페] → 콘텐츠 상세(★ 주요 랜딩)
[구글 검색]   → 지역 가이드
[이메일]      → 콘텐츠 상세 (재방문)

락인 포인트:
  즉시 투표 참여 → 커뮤니티
  북마크 저장    → 소셜 로그인 → 회원가입
  뉴스레터 구독  → ★ 핵심 전환
```

**콘텐츠 상세 페이지가 가장 중요한 랜딩 페이지**  
인스타 링크 클릭 → 콘텐츠 상세 → 구독 CTA가 기본 퍼널.

## 10. 콘텐츠 상세 페이지 기획 (2026-07-01)

**URL**: `/content/[slug]`

### 페이지 구성 (위 → 아래)

| 영역 | 내용 |
|------|------|
| 헤더 | 태그, 제목, 날짜 |
| 메인 콘텐츠 | 타입별 분기 |
| 관련 단지 | 카드 여러 개 (다대다) |
| VS 투표 | 로그인 필수, 즉시 결과 공개 |
| 뉴스레터 CTA | 구독 유도 |
| 다음 콘텐츠 | 추천 2~3개 |

### 콘텐츠 타입 2종

- **카드뉴스** → HTML 슬라이드 뷰어 (PNG 아닌 HTML 렌더링, SEO 대응)
- **기획기사** → Tiptap 블록 에디터, JSON 저장 (텍스트 + 이미지 블록)

### VS 투표

- 어드민에서 질문 제목 / 왼쪽 옵션 / 오른쪽 옵션 직접 입력
- 로그인 후 투표 → 즉시 퍼센트 바 공개
- 락인 포인트 역할 (비로그인 → 로그인 유도)

### DB 구조

```
contents          — id, slug, type(card_news|article), title, tag, body(JSON), published_at
                    vote_question, vote_left, vote_right
content_complexes — content_id ↔ complex_id (다대다)
content_votes     — content_id, user_id, choice(left|right)
```

### 콘텐츠 상세 페이지 세부 결정 (2026-07-29 확정)

| 항목 | 결정 |
|------|------|
| 랭킹 인포그래픽 타입 | **`card_news` 타입에 통합**, `tag="랭킹"`으로 구분 — 둘 다 자동생성·멀티슬라이드
  구조가 동일해 HTML 슬라이드뷰어 컴포넌트를 그대로 재사용. 인스타 스토리용 9:16
  비율은 콘텐츠 타입이 아니라 템플릿 선택(레이아웃)으로만 분기 |
| 공유 기능 | **카카오톡 공유 + 링크 복사 버튼 둘 다 추가** (Kakao SDK + clipboard API) —
  바이럴 성장 전략과 직결되는 저비용 고효과 기능 |
| OG 이미지 | **카드뉴스는 첫 슬라이드를 OG 이미지로 사용.** 기획기사(article)는 첫
  슬라이드가 없으므로 제목 기반 생성 OG 카드(`@vercel/og` 등)로 별도 처리 |

## 12. 인프라·연동 결정 (2026-07-29)

카드뉴스 파이프라인 실사용 확인: `card-news/`가 별도 Node 프로젝트로
`fetch-data.js`(데이터 조회) → `templates.js`(HTML 생성) → `capture.js`
(Puppeteer PNG 캡처) → `post-instagram.js`(인스타 포스팅) 단계로 분리돼
있음. 창부레터는 `capture.js` 단계를 건너뛰고 `fetch-data.js`+`templates.js`를
재사용해 **HTML로 직접 렌더링**하면 됨 — §10의 "카드뉴스 → HTML 슬라이드
뷰어(PNG 아닌 HTML, SEO 대응)" 계획과 정확히 일치.

| 항목 | 결정 |
|------|------|
| Supabase 공유 | **같은 프로젝트 재사용** — `favorites`/`ad_campaigns`에 이미 쓰는
  `site_id` 분리 패턴을 확장, 창부레터용 `site_id='changbuletter'` 추가 예정
  (`supabase/migrations/20260715000001_realtrade_story_site_scoping.sql` 패턴 참고).
  카드뉴스 원본 데이터(`transactions`/`complexes`)도 별도 동기화 없이 바로 조회 가능 |
| 관련 단지 카드 ↔ 실거래이야기 연동 | **가격 미리보기 카드** — 최신가·변동률을 카드에
  표시(예: "84A 8.5억, 최근 3개월 -2%"). ~~두 사이트 간 API 계약 필요~~ →
  **2026-07-29 단순화, 아래 §13 참고** — Supabase 공유 결정 덕분에 HTTP API 불필요,
  창부레터가 `complexes`/`transactions`를 직접 조회 |
| 인증/구독 분리 | 뉴스레터 구독은 **로그인 없이 이메일만**으로 전환장벽 최소화.
  VS 투표·북마크처럼 로그인이 필요한 기능은 danjiondo/realtrade-story와 공유하는
  기존 계정 시스템(`auth.users`/`profiles`) 재사용 |
| 저장소 부트스트랩 | realtrade-story와 동일 패턴 — **별도 세션/도구에서 GSD
  `/new-project`**로 시작. 이 bds 세션과 무관하게 진행 |

### 결정 사항

| 항목 | 결정 |
|------|------|
| 홈 피드 변형 | **변형 A(매거진형)로 확정** — 콘텐츠 브랜드 신뢰감 우선. 변형 B(데이터형,

| 네비게이션 | "단지 검색"·"지도" **완전 제거**, 4개만 유지: 홈 / 콘텐츠 / 지역가이드 /
  마이페이지 (지난 세션 결정과 일치) |
| 관련 단지 가격 미리보기 연동 | **HTTP API 불필요로 단순화**. Supabase 프로젝트를
  bds/실거래이야기와 공유하기로 이미 결정했으므로, `complex_id`가 세 프로젝트에서
  동일한 값(같은 Golden Record) — 창부레터가 `complexes`/`transactions`를
  Supabase 클라이언트로 직접 조회하면 됨. 실거래이야기가 이미 쓰는 가격 계산
  RPC/컬럼(`avg_sale_per_pyeong`, `price_change_30d` 등)을 그대로 재사용 —
  두 사이트 간 API 계약·인증·별도 네트워크 홉 자체가 사라짐(어제 "API 계약 설계
  필요"로 남겼던 항목보다 더 나은 방향으로 해소) |

## 15. SEO 전략 구체화 (2026-07-29 확정)

기존엔 "지역가이드 = 롱테일 SEO"라고만 되어있고 실제 전략이 비어있었음.

### 타겟 키워드 — "지역+맥락" 롱테일, 시세 조회 아님

**중요한 구분**: "창원시 의창구 OO아파트 시세" 같은 **단건 가격 조회형 검색어는
창부레터의 SEO 타겟이 아니다** — 그건 실거래이야기(`/complex/[id]`)의 몫이다.
창부레터는 §11에서 이미 데이터 조회 기능을 안 만들기로 했으므로, "OO아파트
시세"류 키워드로 실거래이야기·호갱노노·아실과 정면승부하는 건 애초에 범위 밖.

창부레터가 노려야 할 건 **대형 데이터 서비스가 절대 안 만드는 지역 맥락형
콘텐츠**(BRIEF §2 "호갱노노가 못 만드는 우리 동네 이야기"와 동일 원칙):
- "창원 의창구 학군 정보", "장유 신도시 분양 전망", "삼성·포스코 임직원 이사 가이드"
- 지역+니즈 조합("창원 이사", "김해 아파트 시세"—단, 이건 오가닉하게 지역가이드
  안에서 실거래이야기로 딥링크하는 방식으로만 다룸)

### URL 구조

계층형 슬러그, 동 단위까지 세분화: `/guide/changwon/uichang/jungdong` 식
(시/구/동) — "창원 의창구 중동 이사 가이드" 같은 구체적 검색어에 더 정확히 매칭.

**한글 슬러그 사용 권장** — 효과가 나는 지점이 다름:
- 네이버: 구글보다 URL·도메인의 키워드 일치를 상대적으로 더 반영하는 경향
- 구글: 랭킹은 URL보다 콘텐츠·제목·헤딩이 훨씬 큰 비중이지만, 검색결과에 노출된
  한글 URL이 사용자 클릭률(CTR)을 높이고 이게 다시 랭킹에 간접 기여

우선순위 지역: 트래픽 수요가 큰 곳부터(신도시·직장 밀집지역 — 중동·용지동·장유),
나머지는 순차 확장.

### 기술 요소

- SSR/SSG 필수 (디자인 핸드오프 README에 이미 명시 — 재확인)
- `sitemap.xml` 자동 생성
- 구조화 데이터(JSON-LD) — 기획기사는 `Article` 스키마, 지역가이드는
  `Article` + 필요 시 `LocalBusiness`류 스키마 검토
- OG 이미지는 §13에서 이미 결정(카드뉴스 첫 슬라이드 / 기획기사는 생성 OG 카드)

### 참고: 실거래이야기 쪽 SEO 노트 (제안, 이 저장소 결정 아님)

단지 상세 페이지 슬러그도 같은 한글 슬러그 원칙 적용 권장:
`/complex/창원-의창구-중동유니시티4단지-48121` 식 (사람이 읽을 수 있는 이름 +

  초안을 자동 조립하고, 발송 전 에디터에서 한마디·순서만 손봄. 매주 발송 부담을

| **구독자 데이터** | **공유 Supabase에 자체 테이블**(이메일·동의일시·상태 등).
  Resend는 발송만 담당 — 데이터 소유권을 유지해야 사이트 내 구독자 통계·분석이
  가능하고, 나중에 발송 서비스를 바꿔도 마이그레이션이 쉬움. Resend Audiences에
  목록 관리를 위임하지 않음 |

  발송 품질(반송률·스팸 신고)을 보호하고, §17 정보통신망법 수신동의의 증명자료로도
  유효. 전환율이 약간 낮아지는 대가는 감수 |

## 21. 개발 로드맵 / MVP 범위 (2026-07-29 확정)

§8의 원래 우선순위 5개를, §14~20에서 정한 내용을 반영해 MVP 기준으로 재배치.

### MVP — 오픈 시점에 반드시 있어야 하는 것

1. **콘텐츠 상세 페이지** (`/content/[slug]`) — 카드뉴스 HTML 슬라이드 뷰어 +
   기획기사 렌더링, 공유 버튼(카카오톡·링크복사), OG 이미지 (§10·§13)
2. **홈 (변형 A 매거진형)** — 콘텐츠 피드 (§13)
3. **구독 폼 + 더블 옵트인 + 개인정보처리방침** (§17·§20)
4. **어드민: Tiptap 에디터 + 미리보기 + 임시저장** (§19)
5. **콘텐츠 목록** (`/content`)

### MVP 직후 — 오픈 후 빠르게

6. **뉴스레터 실제 발송** — 첫 발송은 구독자가 어느 정도 쌓인 뒤여도 됨
7. **VS 투표 + 북마크** — 로그인 연동 필요 (§18)

### 나중에

8. **지역 가이드** — SEO 핵심 자산(§15)이지만 콘텐츠 제작 자체에 시간이 많이 들어
   오픈 필수는 아님. 오픈 후 지역별로 순차 확장
9. **관련 단지 가격 미리보기** — 실거래이야기 쪽 진행 상황과 맞물림 (§12·§13)

### 핵심 판단 — 뉴스레터 발송을 MVP에서 뺀 이유

§8 원래 우선순위에서 3번이던 "뉴스레터 발송"을 MVP 밖으로 이동. 구독자가 0명인
상태에서 발송 인프라부터 만드는 건 순서가 뒤바뀐 것 — 오픈 초기엔 **"구독 신청을
받는 것"까지만** 되면 충분하다. 단, 구독 폼과 더블 옵트인은 MVP 필수(오픈 첫날부터
구독자를 모아야 하므로).
