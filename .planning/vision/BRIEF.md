## 한 줄 정의

**창원·김해 사람들이 가장 먼저 읽는 부동산 미디어**

---

## 1. 문제 — 지금 단지온도는 뭐가 문제인가

- 호갱노노 따라 기능만 붙인 "기능 집합체"가 돼버렸다
- 누구를 위한 서비스인지 불명확
- 전국 서비스 대비 기능 부족, 카페 대비 깊이 부족
- **집 살 생각 없으면 들어올 이유가 없다**

---

## 2. 방향 — 왜 로컬 미디어인가

| 자산 | 의미 |
|------|------|
| 창원부동산이야기 카페 **20만 회원** | 이미 독자가 있다 |
| 창원·김해 다루는 로컬 미디어 **경쟁자 0** | 선점 가능 |
| 호갱노노가 절대 못 만드는 **우리 동네 이야기** | 차별화 |

→ 데이터 기능은 콘텐츠 안에 녹인다. 기능 페이지가 아니라 기사 페이지로.

---

## 3. 브랜드 — "창부레터"

- **어원**: 창원부동산이야기 + 레터(뉴스레터)
- **도메인**: changbuletter.com
- **레터**라는 이름이 이메일 구독을 자연스럽게 암시
- 카페 20만 회원 → 뉴스레터 독자로 전환하는 흐름

> **제1 옵션 확정** — 이 이름 기준으로 진행

---

## 4. 타겟

| 우선순위 | 대상 | 특징 |
|---------|------|------|
| **MAIN** | 창원·김해 거주 30~50대 | 이미 내 집 있음, 카페 회원, 동네 소식 소비 |
| **MAIN** | 이 지역 처음 오는 사람 | 삼성·포스코 임직원 이전, 학군·교통 정보 필요 |
| SUB | 로컬 투자자 | 갭투자·재건축, 데이터 기반 |

## 5. 콘텐츠 4종

| 콘텐츠 | 주기 | 채널 | 역할 |
|--------|------|------|------|
| 주간 실거래가 카드뉴스 | 주 1회 | 인스타 + 카페 | 바이럴, 이미 자동화됨 |
| 기획기사 (동네 분석) | 월 2~4회 | 사이트 + 카페 | 구글 유입·신뢰도 핵심 |

## 10. 콘텐츠 상세 페이지 기획 (2026-07-01)

**URL**: `/content/[slug]`

### 페이지 구성 (위 → 아래)

| 영역 | 내용 |
|------|------|
| 헤더 | 태그, 제목, 날짜 |
| 메인 콘텐츠 | 타입별 분기 |
| 관련 단지 | 카드 여러 개 (다대다) |
| VS 투표 | 로그인 필수, 즉시 결과 공개 |
| 뉴스레터 CTA | 구독 유도 |
| 다음 콘텐츠 | 추천 2~3개 (알고리즘은 아래 참고) |
| 카페 유도 | "카페에서 이 주제로 이야기하기 →" (§18) |

### 콘텐츠 타입 2종

- **카드뉴스** → HTML 슬라이드 뷰어 (PNG 아닌 HTML 렌더링, SEO 대응)
- **기획기사** → Tiptap 블록 에디터, JSON 저장 (텍스트 + 이미지 블록)

### VS 투표

- 어드민에서 질문 제목 / 왼쪽 옵션 / 오른쪽 옵션 직접 입력
- 로그인 후 투표 → 즉시 퍼센트 바 공개
- 락인 포인트 역할 (비로그인 → 로그인 유도)

### DB 구조

> ⚠️ **이 스키마는 §23-6에서 확장됨** — 아래는 07-01 초안이고, 이후 결정(임시저장·
> 예약발행·지역 추천·북마크·구독자)을 담지 못한다. **현행 스키마는 §23-6 참고.**

```
                    vote_question, vote_left, vote_right

```

### 콘텐츠 상세 페이지 세부 결정 (2026-07-29 확정)

| 항목 | 결정 |
|------|------|
| 랭킹 인포그래픽 타입 | **`card_news` 타입에 통합**, `tag="랭킹"`으로 구분 — 둘 다 자동생성·멀티슬라이드
  구조가 동일해 HTML 슬라이드뷰어 컴포넌트를 그대로 재사용. 인스타 스토리용 9:16

  기준입니다. 최신 시세는 여기서 →"(실거래이야기 링크) 배너를 자동 노출. 쌓아둔

## 15. SEO 전략 구체화 (2026-07-29 확정)

기존엔 "지역가이드 = 롱테일 SEO"라고만 되어있고 실제 전략이 비어있었음.

### 타겟 키워드 — "지역+맥락" 롱테일, 시세 조회 아님

**중요한 구분**: "창원시 의창구 OO아파트 시세" 같은 **단건 가격 조회형 검색어는
창부레터의 SEO 타겟이 아니다** — 그건 실거래이야기(`/complex/[id]`)의 몫이다.
창부레터는 §11에서 이미 데이터 조회 기능을 안 만들기로 했으므로, "OO아파트
시세"류 키워드로 실거래이야기·호갱노노·아실과 정면승부하는 건 애초에 범위 밖.

창부레터가 노려야 할 건 **대형 데이터 서비스가 절대 안 만드는 지역 맥락형
콘텐츠**(BRIEF §2 "호갱노노가 못 만드는 우리 동네 이야기"와 동일 원칙):
- "창원 의창구 학군 정보", "장유 신도시 분양 전망", "삼성·포스코 임직원 이사 가이드"
- 지역+니즈 조합("창원 이사", "김해 아파트 시세"—단, 이건 오가닉하게 지역가이드
  안에서 실거래이야기로 딥링크하는 방식으로만 다룸)

### URL 구조

계층형 슬러그, 동 단위까지 세분화: `/guide/changwon/uichang/jungdong` 식
(시/구/동) — "창원 의창구 중동 이사 가이드" 같은 구체적 검색어에 더 정확히 매칭.

**한글 슬러그 사용 권장** — 효과가 나는 지점이 다름:
- 네이버: 구글보다 URL·도메인의 키워드 일치를 상대적으로 더 반영하는 경향
- 구글: 랭킹은 URL보다 콘텐츠·제목·헤딩이 훨씬 큰 비중이지만, 검색결과에 노출된
  한글 URL이 사용자 클릭률(CTR)을 높이고 이게 다시 랭킹에 간접 기여

  이메일 수집 동의 문구에 이 부분을 미리 포함해둘 것

### 개인정보처리방침

- 이메일만 수집해도 개인정보보호법상 처리방침 페이지 필요(수집 항목·목적·보유기간
  명시)

### 표시광고법

- 협찬 기획기사·광고는 "광고" 라벨 명확히 표시
- §14 확장기 진입 시, 카피 가이드의 "광고 없음" 신뢰 신호 문구를 "제휴 콘텐츠는
  광고 표시" 식으로 수정 필요(초기 카피 그대로 두면 확장기에 모순 발생)

### 선례 — 반복하지 말 것

realtrade-story 리서치 때 danjiondo(단지온도)의 기존 법적 문서(개인정보처리방침·
이용약관)가 "초안 — 법무 검토 전" 상태로 방치돼 있었고 사업자 정보(상호·대표자·
사업자등록번호)조차 없다는 게 발견된 바 있음(`02-realtrade-story.md` §10 항목6).
창부레터는 **론칭 전 최소한 이메일 수집 동의 문구 + 개인정보처리방침 초안을 필수
준비물로** 둔다 — 나중으로 미루지 않음.

## 20. 뉴스레터 발송 설계 (2026-07-29 확정)

§8 우선순위 3번. 기존엔 "Resend API 사용" 외에 비어있던 부분.

| 항목 | 결정 |
|------|------|
| **본문 구성** | **자동 생성 + 수동 편집** — 지난주 콘텐츠·주간 카드뉴스 데이터로
  초안을 자동 조립하고, 발송 전 에디터에서 한마디·순서만 손봄. 매주 발송 부담을
  낮추면서도 "레터"라는 브랜드 약속(사람 목소리)을 유지 |
| **구독자 데이터** | **공유 Supabase에 자체 테이블**(이메일·동의일시·상태 등).
  Resend는 발송만 담당 — 데이터 소유권을 유지해야 사이트 내 구독자 통계·분석이

  목록 관리를 위임하지 않음 |
| **더블 옵트인** | **적용** — 이메일 인증 후 구독 확정. 오타·허위 이메일을 걸러
  발송 품질(반송률·스팸 신고)을 보호하고, §17 정보통신망법 수신동의의 증명자료로도
  유효. 전환율이 약간 낮아지는 대가는 감수 |
| 발송 주기 | 주 1회, 월요일 아침 (디자인 핸드오프 카피에 이미 "매주 월요일 아침,

| 수신거부 | 매 발송 시 옵트아웃 링크 필수 (§17) |

**§19 예약 발행과의 연결**: 기획기사 예약 발행 시각을 월요일 발송 직전으로 맞추면,

## 21. 개발 로드맵 / MVP 범위 (2026-07-29 확정 / §23 감사 반영)

§8의 원래 우선순위 5개를, §14~20에서 정한 내용을 반영해 MVP 기준으로 재배치.

> ⚠️ **§23 전수감사 반영**: 아래 MVP 항목들이 의존하는 인프라가 실제로는 없다는 게
> 확인돼, **0단계(선행 조건)를 신설**했다. 0단계 없이 MVP를 시작하면 첫날 막힌다.

### 0단계 — MVP 선행 조건 (§23-2·§23-7)

이 단계가 끝나기 전에는 창부레터 저장소를 부트스트랩해도 진도가 안 나감:

| # | 작업 | 소관 |
|---|------|------|
| 0-1 | **도메인 구매 → DNS/SPF/DKIM → Resend 발신 도메인 인증** | 사용자 + 창부레터 |
| 0-2 | **Supabase Pro 전환** (현재 free 470/500MB — 자매 프로젝트 하드 게이트) | 사용자 |
| 0-3 | **카드뉴스 슬라이드 데이터를 Supabase에 저장하는 단계 추가** | **bds (이 저장소)** |
| 0-4 | **`site_id` CHECK 제약에 `'changbuletter'` 추가** 마이그레이션 | **bds (이 저장소)** |
| 0-5 | **DB 스키마 확정** — `contents`(status·scheduled_at·category·region_tags·
  excerpt·read_minutes·cover_image), `subscribers`, `content_bookmarks` (§23-6) | bds |
| 0-6 | 카드뉴스 템플릿 창부레터 브랜드로 리브랜딩 + 인스타 계정 통일 (§23-1) | bds |
| 0-7 | Cloudflare R2 버킷 생성 (이미지 저장소, §23-7) | 창부레터 |

### MVP — 오픈 시점에 반드시 있어야 하는 것

1. **콘텐츠 상세 페이지** (`/content/[slug]`) — 카드뉴스 HTML 슬라이드 뷰어 +
   기획기사 렌더링, 공유 버튼(카카오톡·링크복사), OG 이미지 (§10·§13)
   → **슬라이드 뷰어는 `templates.js` 재사용이 아니라 React 컴포넌트 신규 작성**(§23-1)
2. **홈 (변형 A 매거진형)** — 콘텐츠 피드 (§13)
   → **랭킹 스트립·지표 패널용 데이터 액세스 레이어 신규 필요**(§23-5) — 평형별
   최신가 쿼리는 `cancel_date IS NULL AND superseded_by IS NULL` 필수(§23-4)
3. **구독 폼 + 더블 옵트인 + 개인정보처리방침** (§17·§20) — 0-1 완료 후 가능
4. **어드민: Tiptap 에디터 + 미리보기 + 임시저장** (§19)
   → **어드민 인증 모델 미정**(§23-7) — 착수 전 결정 필요
5. **콘텐츠 목록** (`/content`)

### MVP 직후 — 오픈 후 빠르게

6. **뉴스레터 실제 발송** — 첫 발송은 구독자가 어느 정도 쌓인 뒤여도 됨
7. **VS 투표 + 북마크** — 로그인 연동 필요 (§18)

### 나중에

8. **지역 가이드** — SEO 핵심 자산(§15)이지만 콘텐츠 제작 자체에 시간이 많이 들어
   오픈 필수는 아님. 오픈 후 지역별로 순차 확장
9. **관련 단지 가격 미리보기** — ~~실거래이야기 쪽 진행 상황과 맞물림~~ →
   **정정(§23-8)**: 쿼리는 창부레터가 직접 짜므로(§13) 실거래이야기 개발 진도와
   무관. 실제 의존은 **딥링크 URL 스킴**인데 실거래이야기는 도메인·Vercel 프로젝트도
   아직 없음 — **MVP 오픈 시 죽은 링크가 나가지 않도록** 링크 숨김 처리 또는
   실거래이야기 배포 선행 필요

### 핵심 판단 — 뉴스레터 발송을 MVP에서 뺀 이유

§8 원래 우선순위에서 3번이던 "뉴스레터 발송"을 MVP 밖으로 이동. 구독자가 0명인
상태에서 발송 인프라부터 만드는 건 순서가 뒤바뀐 것 — 오픈 초기엔 **"구독 신청을
받는 것"까지만** 되면 충분하다. 단, 구독 폼과 더블 옵트인은 MVP 필수(오픈 첫날부터
구독자를 모아야 하므로).

## 23. 전수감사 정정 (2026-07-29) — ⚠️ 실행 전 필독

§1~§22를 실제 코드베이스와 대조 감사한 결과, **§11~§13의 "기존 인프라 재사용"
전제 3건이 전부 사실과 달랐다.** 자매 프로젝트(`02-realtrade-story.md` §10)가
"기존 재사용 가능"이라던 8건이 코드 확인 시 틀렸던 것과 **정확히 같은 패턴**이
반복됨. 아래 정정이 §21 MVP 범위 산정의 새 기준이다.

### 23-1. 카드뉴스 파이프라인 — 재사용 불가, 재작성 필요

§12는 "`capture.js`만 건너뛰고 `fetch-data.js`+`templates.js` 재사용"이라고 했으나
실제 코드(`card-news/scripts/`) 확인 결과:

| 문제 | 실제 |
|------|------|
| **브랜드가 다름** | `templates.js:90,98`이 렌더하는 건 **"창원부동산랩"**, 브랜드
  컬러는 파란색 `--brand: #0066FF`. 창부레터는 딥그린 `#1B4332`+오렌지 — BRIEF
  전체에 "창원부동산랩"이라는 단어가 한 번도 없었음 |
| **컴포넌트가 아님** | `templates.js`는 `<!DOCTYPE html>`로 시작하는 **완성된 HTML
  문서**를 반환하고 `1080px × 1350px` 고정 + 폰트를 `file://` 절대경로로 로드.
  Next.js에 넣으려면 iframe뿐인데 **iframe은 색인 대상이 아니라 "SEO 대응"이라는
  목적 자체가 무산됨** |
| **서비스롤 전용** | `fetch-data.js`는 `SUPABASE_SERVICE_ROLE_KEY`가 없으면 import
  시점에 throw. 프론트엔드에 서비스롤 키를 넣는 건 금지(`04-infra-integration.md`)
  → anon+RLS 기준 쿼리 신규 작성 필요 |
| **9:16 템플릿 없음** | §13 "인스타 스토리 9:16은 템플릿 선택으로 분기"라고 했으나
  `capture.js`는 4:5(1080×1350) 고정, 9:16 템플릿은 존재하지 않음 |

**결정**: **브랜드를 창부레터로 통합** — 카드뉴스 템플릿을 딥그린+오렌지로 리브랜딩,
인스타 계정(`@cb_letter`)도 창부레터로 통일. 웹 슬라이드 뷰어는 템플릿을 React
컴포넌트로 재작성(iframe 아님, 반응형). 브랜드 자산이 한 곳으로 모이는 대신,
운영 중인 계정 브랜딩 변경이므로 기존 팔로워 안내 필요.

### 23-2. 카드뉴스 데이터가 DB에 없음 — MVP #1의 선행 조건

- `supabase/migrations/` 전체에 `card_news`/`contents` 테이블 **0건** (확인 완료)
- `generate.js`에 Supabase write **0건** — Supabase에 올라가는 건 인스타 업로드용
  완성 PNG뿐. 산출물은 GitHub Actions 아티팩트 `retention-days: 30`
- 따라서 **§16의 "카드뉴스 몇 주치 아카이브 확보 후 오픈"이 현재로선 불가능**
- §5의 "이미 자동화됨"도 과장 — 인스타 포스팅은 `workflow_dispatch` 수동 게이트이고
  **카페 배포 자동화는 아예 없음**

**결정**: **bds 파이프라인에 "슬라이드 데이터를 Supabase에 저장" 단계를 추가**한다.
이건 이 저장소(bds) 작업이므로 창부레터 부트스트랩 전에 선행되어야 함 — §21
로드맵에 **MVP 선행 작업**으로 편입.

### 23-3. `site_id='changbuletter'`는 DB 제약에 막힘

`20260715000001_realtrade_story_site_scoping.sql`:
```sql
check (site_id in ('danjiondo', 'realtrade-story'))
```
`'changbuletter'` insert는 **제약 위반으로 실패**한다. 마이그레이션 추가는 bds
소관이므로 크로스 저장소 작업(설정 플래그가 아님).

추가 문제: §18 "북마크 유지"는 `favorites` 테이블을 전제하는데, 그 테이블은
`complex_id` 기반이다. **창부레터가 북마크하는 대상은 단지가 아니라 콘텐츠**라
스키마가 맞지 않음 → 별도 테이블 필요(§23-6 참고).

### 23-4. `avg_sale_per_pyeong` / `price_change_30d`는 RPC가 아니라 컬럼

§13이 "실거래이야기가 이미 쓰는 가격 계산 RPC"라고 했으나:
- **컬럼이다** (`20260516000001_phase11_map_columns.sql`에서 `complexes`에 추가,
  배치 함수 `refresh_complex_price_stats()`가 채움)
- **실거래이야기는 이걸 쓰고 있지 않다** — 그 저장소 코드는 삭제 후 재시작 중
  (`05-handoff-notes.md` §3). 실사용처는 bds/단지온도
- **§13이 약속한 값을 못 만든다**: `avg_sale_per_pyeong`은 단지 전체 평당가(평형별
  최신 실거래가 아님), `price_change_30d`는 30일 롤링(3개월 아님). 자매 프로젝트가
  §10 항목5에서 정확히 이 착각으로 데인 지점
- **평형별 최신가는 `transactions` × `complex_area_types` 신규 쿼리**이며,
  CLAUDE.md 필수 규칙 **`cancel_date IS NULL AND superseded_by IS NULL`**을 반드시
  포함해야 함(취소·정정 거래가 현재가로 노출되는 사고 방지)
- **숨은 결합**: 이 컬럼들은 danjiondo Vercel에 배포된 일배치가 갱신한다. danjiondo를
  sunset하면 창부레터 홈 히어로·랭킹이 조용히 얼어붙음 — 소유권 이전 필요

### 23-5. §11 "데이터 조회 기능 안 만듦"은 과장 — 범위 산정이 낙관 편향

§11/§6 무효박스의 "창부레터는 데이터 조회 기능을 아예 만들지 않는다"와, §13이
유지하기로 한 것들(홈 랭킹 스트립·사이드 지표 패널·관련 단지 가격 미리보기,
`data.js`의 `weekly`/`volumeRank`/`riseRank`)이 정면 충돌한다. 이것들은 전부
데이터 조회다.

**정정된 표현**: 창부레터에 없는 건 **탐색 기능**(단지 검색·지도·단지상세)이지
데이터 조회 자체가 아니다. **창부레터도 랭킹 집계·주간 집계·평형별 최신가 쿼리를
갖는 데이터 액세스 레이어가 필요하다** — §21 MVP 범위는 이걸 반영해 재산정해야 함.

### 23-6. `contents` 스키마(§10)가 이후 결정을 담지 못함

| 누락 | 필요 이유 |
|------|----------|
| `status`(draft/published), `scheduled_at` | §19 임시저장·예약발행이 MVP 필수(§21 #4) |
| `category` + `region_tags` **분리** | §5 정정이 `tag`를 타입 구분용(`"랭킹"`)으로
  징발해서, 하나의 `tag` 컬럼이 "랭킹"이면서 동시에 "의창구"일 수 없음 → §13의
  "같은 지역 태그 우선" 추천 알고리즘이 성립 불가. **결정: `category`(랭킹/동네분석/
  분양뉴스…) + `region_tags`(배열: 의창구·중동…) 두 필드로 분리** — 디자인 `data.js`도
  `cat`/`tag`를 이미 별개로 쓰고 있어 목업과도 일치 |
| `excerpt`, `read_minutes`, `cover_image` | 디자인 목업이 요구하는 필드(요약문·읽는
  시간·썸네일)가 스키마에 없음 |
| `subscribers` 테이블 | §20이 "자체 테이블(이메일·동의일시·상태)"로 결정했으나
  **테이블 정의가 문서 어디에도 없음** |
| `content_bookmarks` 테이블 | §23-3 — `favorites`는 단지용이라 콘텐츠 북마크에
  못 씀 |

⚠️ 이 스키마들은 **운영 중인 서비스 2개가 함께 쓰는 공유 프로덕션 DB**에 들어간다.
실행 세션이 즉석 설계하지 않도록 부트스트랩 시점에 먼저 확정할 것.

### 23-7. 인프라 선행 조건 (실행 첫날 막히는 지점)

| 항목 | 결정 |
|------|------|
| **도메인·Resend를 MVP 0번으로** | 더블 옵트인(§20·§21 #3)은 그 자체가 트랜잭션
  이메일 발송이라, §21의 "발송 인프라는 MVP 밖" 선언과 모순이었음. 선행 체인:
  **도메인 구매 → DNS/SPF/DKIM → Resend 발신 도메인 인증 → 확인메일 템플릿**.
  (`bds`의 `RESEND_API_KEY`는 현재 비어있음 — 창부레터용 신규 설정 필요) |
| **Supabase Pro 전환** | 공유 프로젝트가 free 470MB/500MB로 한계. 자매 프로젝트가
  이미 "공개 런칭 전 Pro 활성화"를 **하드 게이트**로 지정한 상태(`02` §10 항목4).
  창부레터도 동일 게이트 적용 — DB 용량·백업·성능 목적 |
| **이미지는 Cloudflare R2** | Pro 전환과 별개로 이미지는 공유 Supabase Storage가
  아니라 **R2에 분리**(§22 수정). 이유: ① R2는 egress 무료 — 사진 중심 매거진에
  SEO 트래픽이 붙으면 Supabase는 대역폭 초과 과금 ② 세 프로젝트가 한 DB를 쓰므로
  이미지 증가가 danjiondo·실거래이야기 용량까지 압박(실거래이야기가 이미 용량 때문에
  부산 백필 중단한 전례) ③ 업로드 API 한 번 붙이면 되고 `next/image`는 동일 동작 |
| **크론은 창부레터 자체 GitHub Actions** | 예약발행(§19)·주간 뉴스레터(§20)에 최소
  2개 스케줄러 필요. Vercel Hobby는 1일 1회 한도라 bds가 이미 같은 이유로 GitHub
  Actions를 쓰는 검증된 패턴 — 창부레터 저장소에서 독립 관리, bds에 부담 안 줌 |
| **어드민 인증 모델** | §12는 독자 인증만 결정했고 **어드민 권한 모델은 정의된 적
  없음**. 공유 `profiles`에 admin 역할을 얹을지(bds에 이미 어드민 콘솔·역할 모델
  존재) 부트스트랩 시점에 결정 필요 |

### 23-9. 편집 원칙 — 실명 단지 평가 기사의 분쟁 리스크

§18은 "부동산 시세 관련 명예훼손·허위사실 유포 분쟁이 빈발"을 근거로 댓글을

"장유 신도시, 김해의 강남이 될 수 있을까" — 실명 단지 평가). §17은 이메일법·
표시광고법만 다뤄 불균형이었음.

**추가 원칙**:
- 모든 시세·거래 주장에 **데이터 근거 명시**(출처·기간·집계 기준)
- 단정적 예측 표현 금지("오른다" → "이런 요인이 있다"), 투자 권유·수익 보장 표현
  금지(기존 카피 가이드와 동일)
- **정정 절차 문서화** — 오류 지적 접수 경로 + 정정 시 기사에 정정 이력 표기
- 인터넷신문 등록(신문법) 필요성은 **§14 확장기(광고 도입) 시점에 재검토** —
  정기 발행 + 광고 수익 구조가 되면 검토 대상
