# A. Notify Worker — (d) 를 제안합니다: **일 1회로 낮춘다**

## A-0. 왜 (a)(b)(c) 가 아닌가

### (a) Vercel Cron 이관 — **이미 막혀 있습니다**

`vercel.json` 을 확인했습니다. **Hobby 크론 2개를 이미 다 썼습니다.**

```json
"crons": [
  { "path": "/api/cron/daily",         "schedule": "0 19 * * *" },
  { "path": "/api/cron/cafe-articles", "schedule": "30 19 * * *" }
]
```

그리고 **Hobby 플랜 크론은 하루 1회만 돕니다.** 슬롯이 남아 있었어도 5분 주기는 불가능합니다.
→ Pro 업그레이드 없이는 선택지가 아닙니다.

### (b) 외부 스케줄러 — **5분 주기를 충실히 재현하는데, 그 주기가 과잉입니다**

`notifications` 테이블에 **insert 하는 곳을 전부 찾았습니다. 둘뿐이고 둘 다 배치입니다.**

| 생산자 | 입력 | 주기 |
|---|---|---|
| `generate-alerts.ts` | `transactions` (= `/api/cron/daily` 가 **하루 한 번** 적재) | 일 1회 |
| `digest.ts` | `favorites` → 주간 요약, ISO 주차로 dedupe | **주 1회** (월 09:00 KST) |

**실시간으로 알림을 만드는 경로가 없습니다.** 사용자 동작이 `notifications` 에 행을 넣는 곳은 없습니다
(테스트 파일 제외하고 전수 확인). 즉 **발송을 하루 1회로 묶어도 잃는 것이 없습니다.**

> **하루 한 번 바뀌는 데이터를 5분마다 들여다보고 있었습니다.**
>
> 이게 **발화율 2% 가 지금까지 눈에 띄는 피해를 안 낸 이유**입니다.
> 288회 중 286회는 어차피 볼 게 없었습니다.

외부 의존을 하나 늘려서 재현할 가치가 없는 주기입니다.

### (c) 현상 유지 + 문서화 — **"최대 8시간 지연"은 사양이 아니라 무작위입니다**

적는다고 통제되지 않습니다. 지금 구조에서는 **카카오 알림이 새벽 3시에 나갈 수 있습니다**
(`deliver.ts` 에 시간대 가드가 없고, 실측 간격이 무작위 4시간이므로).

## A-1. 제안 — cron 한 줄을 바꿉니다

> ⚠️ **처음에 08:00 KST(`0 23 * * *`)를 적었다가 10:00 KST(`0 1 * * *`)로 바꿨습니다.**
> `weekly-digest.yml`이 **월요일 09:00 KST**에 `notifications` 에 행을 넣는데(`buildWeeklyDigest`),
> 08:00 발송이면 그 주간 요약이 **23시간 뒤인 화요일 아침**에 나갑니다. 매주 하루씩 밀립니다.
> **10:00 으로 두면 월요일 09:00 digest 가 1시간 뒤에 나갑니다.**

```diff
  on:
    schedule:
-     # 매 5분마다 실행 (KST 06:00-24:00 = UTC 21:00-15:00)
-     - cron: '*/5 * * * *'
+     # 매일 10:00 KST (UTC 01:00)
+     #   - MOLIT 일배치(19:00 UTC = 04:00 KST) 6시간 뒤
+     #   - Weekly Digest(월 00:00 UTC = 09:00 KST) 1시간 뒤
+     - cron: '0 1 * * *'
    workflow_dispatch: {}
```

### 근거 — **그쪽 리포의 실측입니다**

최근 스케줄 실행 98건(4.41일)을 선언 주기별로 묶었습니다.

| 워크플로 | 선언 | 실측/일 | **발화율** |
|---|---|---|---|
| MOLIT 일배치 · 데이터 신선도 점검 · Cafe Ingest · Complex Integrity · Refresh Price Stats · 지오코딩 | **일 1회** | 1.13 | **100% (누락 0)** |
| Rankings Cron | 매시 (24) | 4.99 | **21%** |
| **Notify Worker** | **5분 (288)** | 5.22 | **2%** |

> **짧게 선언할수록 더 많이 흘립니다.** 그리고 **일 1회는 그쪽 리포에서 한 번도 안 빠졌습니다.**

이쪽(ax-sub)도 같은 걸 세 번 봤습니다 — 2시간 주기 29%(ADR-027), `collect-gmail` 36%(ADR-028),
그리고 이번 5분 주기 2%. ADR-028 의 교훈이 그대로 적용됩니다:
***"클라우드로 옮기는 것만으로는 부족하고 무엇이 깨우느냐가 같이 중요하다."***

### 이 한 줄로 동시에 해결되는 것

| | |
|---|---|
| 발화 신뢰도 | 2% → **100%** |
| 발송 시각 | 무작위 → **매일 08:00 KST 고정**. 새벽 카카오 발송이 사라집니다 |
| 데이터 정합 | 적재(04:00) 4시간 뒤라 **그날 데이터가 반영된** 알림이 나갑니다 |
| 크론 개수 | 안 늘어납니다 (Vercel 2/2 유지) |
| 외부 의존 | 안 늘어납니다 |
| 변경량 | **1줄** |

# B. 월간 AI 해설 — **2026-10-07(수) 01:00 UTC = 10:00 KST** 를 권합니다

## B-1. 왜 그 시점인가

Groq 를 쓰는 워크플로를 전부 찾아 TPD 충돌을 피했습니다.

| 워크플로 | 크론 | UTC 요일 |
|---|---|---|
| `crawl-presale.yml` | `0 21 * * 2,4` | **화 · 목** |
| `weekly-regional-commentary.yml` | `0 21 * * 0` | **일** |
| `monthly-ai-commentary.yml` | `0 20 1 * *` | 매월 1일 |

→ **수요일 UTC 에는 Groq 워크플로가 하나도 없습니다.**

| | |
|---|---|
| 01:00 UTC 시작 | TPD 는 00:00 UTC 리셋 → **200K 전부** 쓸 수 있습니다 |
| 42분 소요 예상 | **11:00 KST 에 결과 확인** — 한국 근무 시간입니다 |
| ⛔ 오늘(화) 금지 | 21:00 UTC `crawl-presale` 과 **같은 TPD 일자**를 공유합니다 |

## B-2. 보너스 — ③번이 공짜로 교차 검증됩니다

같은 날 **23:00 UTC 에 `데이터 신선도 점검`이 돕니다.**
10-07 01:00 UTC 에 실행하면, 22시간 뒤 그 점검이 `data_sources.monthly-commentary` 를 읽습니다.

→ **`markCronStatus` 가 실제로 기록됐는지를 사람이 확인할 필요 없이 파이프라인이 스스로 확인합니다.**
10-08 아침 감시견 보고에 그 결과가 그대로 올라옵니다.

## B-3. 확인할 것 (재확인)

| | 기대값 | 어디서 보나 |
|---|---|---|
| ① 창원 우선 | 창원 5,051행이 **먼저** 처리되고 **100% 덮임** | 실행 로그 |
| ② 깨끗한 중단 | `TpdExhaustedError` 즉시 탈출, **42분 안팎** (120분 타임아웃 아님) | 실행 시간 |
| ③ `markCronStatus` | `partial` + `reason=groq_tpd_exhausted` | `data_sources` → **10-08 감시견 보고** |

**예상 결과는 "성공"이 아니라 `status=partial` 입니다.** 200K TPD 로 2,059 전체는 못 덮습니다.
**창원이 100% 면 통과**입니다.
