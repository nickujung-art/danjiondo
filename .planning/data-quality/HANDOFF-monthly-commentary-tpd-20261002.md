> **받는 곳**: `bds` 담당 · **보내는 곳**: `ax-sub`
> **계기**: 어제 인계장(`HANDOFF-predictions-retire-20261001.md`) ③의 검증 시점이 오늘이었다.
> 결과: **실패했고, 원인이 예상과 달랐다.** 그리고 실패한 사실이 감시에 안 잡혔다.

## 🔴 1. 결론부터 — 타임아웃을 늘려도 안 된다. **일일 토큰 한도**다

`Monthly AI Commentary Batch` 2026-10-01 23:44Z 실행이 **2h0m21s 에 `cancelled`**(= `timeout-minutes: 120` 초과).
로그를 열었더니 원인이 명확했다:

```
Rate limit reached for model `qwen/qwen3.8-27b` ... service tier `on_demand`
on tokens per day (TPD): Limit 200000, Used 199715, Requested 482
```

**RPM(분당 요청)이 아니라 TPD(하루 토큰)다.**

| | |
|---|---|
| 조회된 대상 | `[FETCH] 2059건 조회 완료` |
| 단지당 토큰 | **~490** (429 메시지의 `Requested` 값들) |
| Groq 무료 한도 | **200,000 토큰/일** |
| → 하루 처리 가능 | **~500단지 = 전체의 26%** |
| 실제 적재 | 6,350행 / 24,320행 = **26.1%** — 위 계산과 일치 |
| 완주에 필요한 양 | **약 4일치 일일 쿼터** |

**한도는 하루 단위로 리셋된다.** `timeout-minutes` 를 6시간으로 올려도 그날 안에는 더 못 쓴다.
어제 인계장에서 내가 *"왜 4배 느린가"*라고 적었는데 **질문 자체가 틀렸다.** 느린 게 아니라
**예산이 하루에 4분의 1씩만 들어온다.**

## 🟡 2. 고칠 수 있는 버그 — TPD 429 에 재시도하면 안 된다

타임라인:

```
23:45:12  [START] area_bucket=84 limit=0
23:45:32  [FETCH] 2059건 조회 완료
00:27:48  첫 429 (TPD 소진)          ← 시작 42분
01:44:50  Terminate orphan process   ← 타임아웃 SIGKILL
```

**유효한 작업은 42분이고 나머지 78분(전체의 65%)은 이미 소진된 일일 한도에 재시도만 했다.**
`429` 가 로그에 **263회** 찍혔고, 요약 줄은 SIGKILL 때문에 아예 안 나왔다.

`scripts/generate-complex-commentary.ts` 의 재시도 분기가 `rate_limit_exceeded` 를
503·overloaded 와 같이 다룬다. **그 둘은 성질이 다르다**:

- **RPM 429** — 몇 초 뒤 풀린다. 재시도가 맞다
- **TPD 429** — **그날 안에는 안 풀린다.** 재시도는 전부 낭비다

→ 응답 본문에 `tokens per day (TPD)` 또는 `"type":"tokens"` 가 있으면 **즉시 중단하고
"N단지 처리 후 일일 한도 소진"을 보고**해야 한다. 그러면 42분에 깨끗이 끝나고,
무엇보다 **종료 코드와 요약이 남는다**(지금은 SIGKILL 이라 둘 다 없다).

덤: 스크립트 주석이 *"Groq: 30 RPM → concurrency 3, 300ms 간격 (분당 최대 18건)"* 으로
**RPM 만 보고 페이싱을 설계**했다. 실제 병목은 TPD 라 이 페이싱은 병목에 닿지도 않는다.

## 💡 3. 가장 값싼 해법 — **창원을 먼저 돌린다**

대상 2,126단지의 지역 분포를 실측했다:

| | 단지 | 비중 |
|---|---|---|
| 창원 5구 (48121·48123·48125·48127·48129) | **431** | **20.3%** |
| 그 외 (부산 26xxx · 거제 48250 · 양산 48310 등) | 1,695 | 79.7% |

그리고 이번 실행이 덮은 비율:

```
창원    1,323 /  5,051 행   26.2%
그 외   5,027 / 19,269 행   26.1%
```

**순서가 지역을 전혀 고려하지 않는다** — 전부 고르게 26%씩 먹었다. 그래서 창원도 74%가 비었다.

그런데 숫자를 맞춰 보면:

```
창원 전체       5,051행
하루 처리량     6,350행   ← 이번 실행이 실제로 쓴 양
```

**창원만이면 하루 한도 안에서 완주한다**(한도의 79.5%). 순서만 바꿔도 창원은 매달 100% 채워진다.

⚠️ **범위를 창원으로 줄이자는 말이 아니다.** `ax-sub` 위키는 창원만 쓰지만 `bds` 앱은
부산·경남 전역을 서비스하므로 나머지 79.7% 가 bds 에 필요한지는 **bds 판단**이다.
다만 **정렬을 창원 우선으로 두면** 한도가 모자라도 위키가 쓰는 부분은 항상 채워지고,
남은 예산이 나머지로 흘러간다 — 양쪽이 다 이긴다.

## 🟡 7. 부탁 — 배치가 **실패 사유를 감시견이 읽을 수 있는 곳**에 남겨 주세요

오늘 원인(TPD)을 찾은 건 **사람이 로컬에서 로그를 연 덕분**이다.
`ax-sub` 감시견은 그걸 못 한다 — `gh run list` 로 "무엇이 실패했다"까지는 보지만
**로그 조회가 403** 이라 "왜"를 못 본다. 그날 보고가 정확히 이렇게 끝났다:

> `데이터 신선도 점검` 로그는 403으로 열람 못 해 위반 사유 확인 불가

정직한 보고라 더 아프다. 감시견의 가치는 *"사람이 매일 안 봐도 된다"* 인데,
**원인 파악에 매번 사람이 필요하면 그 가치의 절반이 깎인다.**

`ax-sub` 쪽에 `F-04-08` 로 과제화했고, 선택지는 둘이다:

| | 방법 | 평가 |
|---|---|---|
| ① | 루틴에 Actions 로그 읽기 권한을 준다 | 쓰기 권한과는 무관하지만 **열람 범위가 넓어진다** |
| ② | **배치가 실패 요약을 감시견이 이미 읽는 곳에 내보낸다** | 권한을 안 늘린다. 원칙 5와 결이 같다 |

**②를 권한다.** 감시견이 이미 읽고 있는 두 곳이 있다:

- `$GITHUB_STEP_SUMMARY` — `collect-gmail` 이 `[runstat]` 을 여기 쓰는 전례가 있고
  감시견이 그걸 파싱한다. 로그 권한 없이 보인다
- `data_sources.error_message` — 감시견이 매일 전체를 조회한다.
  `markCronFailed(supabase, id, errorMessage)` 가 이미 이 필드를 받는다

구체적으로 월간 해설이라면, TPD 소진 시 이런 한 줄이면 충분하다:

```
[runstat] job=monthly-commentary status=partial done=529 total=2059 reason=groq_tpd_exhausted
```

그러면 감시견이 **"월간 해설이 2,059단지 중 529단지에서 일일 토큰 한도로 멈췄다"** 를
그날 아침에 바로 적을 수 있다. 지금은 "실패했는데 이유는 모름"이 최선이다.

⚠️ 이건 월간 해설만의 요청이 아니라 **앞으로 만드는 배치 전부에 대한 부탁**이다.
새 배치를 만들 때 실패 경로에 요약 한 줄을 남겨 주면, `ax-sub` 가 그걸 읽는다.

## 🔴 9. 정정 — **§7 의 제 요청이 절반 틀렸습니다. Step Summary 는 감시견이 못 읽습니다**

§7 에서 두 경로를 제시했는데, 그중 하나가 **실측해 보니 안 됩니다.**

| 경로 | 감시견이 읽을 수 있나 | 월간 해설이 쓰고 있나 |
|---|---|---|
| Actions 로그 | ✗ **403** | ✓ `console.log(runstat)` |
| `$GITHUB_STEP_SUMMARY` | ✗ **REST API 에 노출되지 않음** | ✓ `4fd8e5f` 로 구현됨 |
| **`data_sources`** | ✓ **매일 14행 전체 조회** | ✗ **행 자체가 없음** |

**Step Summary 가 안 되는 근거** — Actions 잡은 check-run 으로도 보이는데, 그 `output` 이 비어 있다:

```
GET /repos/nickujung-art/routines/check-runs/110173904594
→ {"annotations_count":1,"summary":null,"text":null,"title":null}
```

`collect-gmail` 은 Step Summary 에 `[runstat]` 을 쓰는 워크플로인데도 `summary: null` 이다.
GitHub 은 잡 요약을 **UI 에서만 렌더**하고 REST 로는 주지 않는다.
(그래서 감시견이 `collect-gmail` 에 대해서도 *"개별 `[runstat]`/`sent` 값은 열람하지 않음"* 이라고
매일 적고 있었다 — 안 읽은 게 아니라 **못 읽은 것**이었다.)

**제가 §7 에서 `$GITHUB_STEP_SUMMARY` 를 먼저 제시한 게 잘못이다.** `collect-gmail` 의 전례를
근거로 들었는데, 그 전례가 실제로 작동하는지 확인하지 않고 적었다. 죄송하다.

### 그래서 부탁을 이렇게 고칩니다 — `data_sources` 한 곳이면 됩니다

감시견이 **유일하게 닿는 경로**이고, 이미 **매일 14행을 통째로 읽고 있다.**
오늘 보고에도 이렇게 적혀 나온다:

> `daily-batch` — status=partial, MOLIT API 403 (presale 38건 중 최소 5건 실패), consecutive_failures=0

즉 **행만 있으면 사유까지 자동으로 보고된다. 감시견 프롬프트는 고칠 게 없다.**

필요한 것 두 가지:

1. `data_sources` 에 `monthly-commentary` 행 추가 (현재 14행에 없다 — `regional-commentary` 는
   주간 지역 코멘트라 다른 배치다)
2. `scripts/generate-complex-commentary.ts` 종료 시 그 행을 갱신.
   `src/lib/data/cron-status.ts` 의 `markCronStatus(supabase, 'monthly-commentary', status, errorMessage)`
   가 이미 `success`/`partial`/`failed` 를 받고, `error_message` 도 받는다

   ```
   status  = tpdExhausted ? 'partial' : (failed > 0 ? 'failed' : 'success')
   message = `done=${success} total=${total}` + (tpdExhausted ? ' reason=groq_tpd_exhausted' : '')
   ```

`[runstat]` 출력과 Step Summary 기록은 **그대로 두시면 된다** — 사람이 UI 에서 볼 때 유용하고,
나중에 감시견에 로그 권한이 생기면(`ax-sub` F-04-08 ①) 바로 쓸 수 있다.
다만 **지금 감시견에 닿는 것은 `data_sources` 뿐이다.**

⚠️ 이건 월간 해설만의 이야기가 아니다. §7 에서 *"앞으로 만드는 배치 전부"* 라고 적었는데,
그 부탁의 **목적지를 `data_sources` 로 바로잡는다.** Step Summary 는 사람용이고
`data_sources` 가 감시견용이다.
