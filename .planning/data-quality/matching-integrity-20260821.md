## 2. 근본 원인 — CLAUDE.md 의 CRITICAL 규약이 지켜지지 않고 있었다

`CLAUDE.md` 는 *"`complexes` 가 Golden Record. 단지명 단독 매칭 금지 — 항상 좌표+이름
복합 매칭"* 을 CRITICAL 로 못박는다. 그런데 **거래 연결 경로에서는 지켜지지 않았다.**

`match_complex_by_admin` 의 단계 구성:

```
0단계  별칭 정확 일치          — 동 안 봄
1단계  trigram >= 0.9          — 동 안 봄   ← 대부분 여기서 확정된다
2단계  양방향 LIKE unique      — 동 안 봄
3단계  동 필터 + LIKE unique   — 동 봄 (2단계가 복수일 때만 도달)
```

`p_umd_nm`(동)을 인자로 받으면서 3단계에서만 쓴다. 주석이 사유를 밝힌다 —
*"동 필터 없음 — 기존 매칭 회귀 방지"*. **그 판단 자체는 옳았다**(§5 참조).
문제는 대안 근거 없이 이름에만 의존한 것이다.

### 3-4. 재발 방지 — 필터가 아니라 게이트

`complex_canonical_jibun` 테이블에 **단지별 확정 지번**을 거래 다수결로 물질화한다
(비율 0.6↑ · 표본 5↑). 매칭은 그대로 두되, 지번이 **유일하게** 한 단지를 가리키면
그 단지로 확정한다.

```
이름="메트로시티2차" + 지번=양덕동 84-1 (마산메트로시티 소유)
  지번 없이 → 메트로시티2차아파트   (기존 오답)
  지번 포함 → 마산메트로시티        ✅ 정정
```

갱신은 `refresh-price-stats.yml` 에 얹었다(`refresh_complex_canonical_jibun()`).

### 3-5. 운영권역 밖 단지 9곳 격리 (P1-a)

`status` enum 에 **`out_of_region`** 을 추가했다. `demolished` 재사용은 거부했다 —
철거되지 않은 건물을 철거됐다고 기록하는 것이라 나중에 잘못된 결론을 부른다.
거래 288건은 실재하므로 지우지 않고 `complex_id` 만 끊었다. 즐겨찾기 0 확인 후 처리.

### 3-6. `complex_integrity_counts` 파일화

프로덕션에만 있던 함수를 `supabase db dump` 로 받아 마이그레이션으로 옮겼다
(`20260821140000`). Phase 41 이 "발견 5" 로 기록만 해둔 drift 다.

**파일화의 값이 즉시 증명됐다** — 정의를 못 보면 `empty_kapt` 59→61 의 원인을 판정할 수
없었다. 정의를 보니 `household_count > 0` 조건 때문에 **enrich 가 세대수를 채우면 모수가
넓어지는 것**이었다. 오염이 아니다.

## 4. 🔴 오늘 밟은 함정 — 내일 같은 실수 반복 금지

### F-1. "대상 없음 → 끊기" 는 다필지 단지를 파괴한다

처음엔 *"다수 지번과 다르고 그 지번을 가진 다른 단지도 없으면 오염"* 으로 봤다. **틀렸다.**
큰 단지는 여러 필지에 걸친다:

```
506건  율현마을율하e-편한세상 @ 율하동 1405  (현재: 율현마을율하e-편한세상아파트)
 80건  창원롯데캐슬센텀골드 @ 양덕동 166-44  (이름 완전 동일)
 76건  김해센텀두산위브 @ 선지리 1531        (카카오 72m — 같은 부지)
```

dry-run 이 아니었으면 **정상 연결 2,735건을 파괴**했다. 진짜 판별자는 이름도 역색인
유무도 아닌 **거리**다. 그래서 끊기는 카카오 검증 목록만 받는다(`--unlink-verified`).

### F-2. 게이트가 1차·2차를 뭉갤 뻔했다

첫 게이트가 `limit 1` 이라 한 지번을 여러 단지가 공유할 때 한쪽으로 쏠렸다.
**실측 14그룹 / 31곳:**

```
외동 705      주공1(229건) / 주공2(232건)
구산동 410    김해구산4주공 / 구산5주공
안동 BL-2-2   푸르지오 하이엔드 1단지 / 2차
강동동 "가-"  4개 단지 공유 (블록 표기라 지번 구실 못 함)
```

`matching-ambiguous-20260805.md` 가 이미 경고한 실패 모양이다
(*"목연오피스텔2차를 차수 없는 목연오피스텔에 붙이면 1차·2차가 뭉개진다"*).

**고침: 지번이 정확히 한 단지를 가리킬 때만 게이트가 작동한다.**
충돌하면 꺼지고 이름에 맡긴다 — 차수가 이름에 있으면 이름이 정확한 근거다.

> **두 근거는 상호 보완한다.**
> 이름 같고 지번 다름 → **지번**이 가른다 (메트로시티)
> 지번 같고 차수 다름 → **이름**이 가른다 (주공1/2)

### F-3. `min(uuid)` — 함수가 통째로 죽어 있었다

유일성 검사를 `min(j.complex_id)` 로 썼는데 PostgreSQL 에 `min(uuid)` 집계가 없다.
`match_complex_by_admin` 이 **어떤 인자로도 호출 즉시 실패**했다.

**push 성공은 검증이 아니다.** plpgsql 은 지연 바인딩이라 `CREATE FUNCTION` 이 본문
해석을 실행 시점까지 미룬다. `20260819030000` 이 수습한 것과 같은 부류
(*"search_path='' 인데 미수식 참조라 호출 즉시 죽던 함수 2개"*).
→ **함수를 바꾸면 반드시 호출해서 확인한다.** 실제로 그렇게 해서 즉시 잡았다.

### F-4. `status='inactive'` 는 존재하지 않는 값

enum 은 6단계(`pre_sale`·`under_construction`·`recently_built`·`active`·
`in_redevelopment`·`demolished`)뿐이다. 적용했으면 실패했다.

### F-5. `ALTER TYPE ADD VALUE` 는 같은 트랜잭션에서 그 값을 못 쓴다

`supabase db push` 가 마이그레이션을 트랜잭션으로 감싸므로 enum 추가와 값 사용을
한 파일에 둘 수 없다. 20260821120000(추가) / 20260821130000(사용)으로 분리했다.

### F-6. 매칭 조건도 함께 넓혀야 했다

RPC 가 `status != 'demolished'` 로만 걸러서, 거래를 끊어도 다음 적재가 다시 붙였을 것이다.
`not in ('demolished', 'out_of_region')` 으로 고치고 실증했다(매칭 '고려맨션' @구서동 → 매칭 없음).

## 5. 왜 "1단계에 동 필터"가 답이 아닌가

기존 주석의 판단이 옳았다. 동을 강제하면 정상 데이터가 무너진다:

- 큰 단지는 여러 **법정동**에 걸친다 — 대동다숲(원계리/삼계리)은 카카오 실측 **0m**
- 다필지 단지는 여러 **지번**에 걸친다 — 율하e편한세상 506건

그래서 필터(후보를 좁힘)가 아니라 **게이트**(지번이 확정적일 때만 정정)로 만들었다.

## 8. 하지 말 것

- **`household_count` 백필** — 소스가 없다. 세대수 0/null 480곳 중 K-apt 코드 보유는
  20곳뿐이고, 건축물대장은 `hhldCnt`·`hoCnt`·`fmlyCnt` 가 전부 0으로 온다

  지번(거래 다수결)으로 게이트 보호 중**이다. 문서의 "9.8%" 는 확정지번 테이블이
  생기기 전 값이다
- **카카오 연속 재실행** — 막힌 전례가 있다. 스크립트의 `--max`/`--limit` 을 쓴다
