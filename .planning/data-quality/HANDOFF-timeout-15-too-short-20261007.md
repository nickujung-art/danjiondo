## 1. 숫자

```

```

| | |
|---|---|
| 하루 TPD 한도 | 200K ÷ 490토큰 = **~408건** |
| 분당 18건(코드 주석)이면 | **23분** |

```

실측(11/분)   165건 / 408건  →  40% 에서 잘림
```

## 2. 잘리면 생기는 일 — **우리가 방금 고친 그 버그가 돌아옵니다**

`timeout-minutes` 로 죽으면 잡은 **`cancelled`** 이 됩니다. 그러면 —

```
스크립트가 끝까지 못 감  →  markCronStatus() 가 아예 안 불림
                              ↓
                    data_sources 는 옛 상태 그대로
                              ↓
          신선도 점검은 "갱신 안 됨" 으로 빨강, 사유는 비어 있음
```

**2026-10-01에 정확히 이렇게 됐습니다** — 120분 타임아웃으로 `cancelled` 되고,
`data_sources.monthly-commentary` 가 `null` 로 남아 몇 주간 사유를 못 봤습니다.
`exit(0)` 를 넣어 깨끗이 끝나게 만든 공이 **타임아웃에 먼저 잘리면 무효**가 됩니다.

그리고 매일 돌므로 **매일 `cancelled`** 이 됩니다. 데이터는 조금씩 차지만
**상태는 영원히 갱신되지 않습니다.**

## 3. 부탁 ① — `timeout-minutes: 15` → **60**

```diff
-    timeout-minutes: 15
+    timeout-minutes: 60   # 따라잡는 날 실측 23~37분 + 여유. 평소엔 stale 0건이라 즉시 종료
```

120분보다 훨씬 타이트하면서 잘릴 위험은 없습니다.
**어차피 시간이 아니라 TPD가 먼저 멈춥니다** — 408건에서 `TpdExhaustedError` 로 끝납니다.
타임아웃은 "무한히 매달리는 것"만 막으면 되고, 그 역할은 60분으로 충분합니다.

## 4. 부탁 ② — 크론 시각 `0 20 * * *` → **`0 6 * * *`**

지연을 감안하면 **착지 시각**이 이렇게 됩니다.

| 워크플로 | 선언 | 실측 착지 |
|---|---|---|
| `crawl-presale` | 21:00 | **00:04~00:33** (다음 UTC 날짜) |
| `weekly-regional-commentary` | 21:00 | 22:49~23:54 |
| **`monthly-ai-commentary`(신규)** | **20:00** | **22:00~00:00** ← **같은 창** |

Groq 워크플로 셋이 **전부 같은 두세 시간에 몰립니다.**
따라잡는 1~2일차에 하필 겹치면 서로 TPD를 뺏습니다.

```diff
-    - cron: '0 20 * * *'   # 매일 05:00 KST
+    - cron: '0 6 * * *'    # 매일 15:00 KST — 착지 08:00~10:00 UTC, 저녁 무리와 분리
```

06:00 UTC 대에는 **Groq를 쓰는 워크플로가 하나도 없습니다.**

> 이건 ①보다 덜 급합니다. **①만 먼저 고치셔도 됩니다.**
> 다만 따라잡기가 끝나기 전(1~2일차)에는 충돌 영향이 있으니 같이 고치는 게 낫습니다.
