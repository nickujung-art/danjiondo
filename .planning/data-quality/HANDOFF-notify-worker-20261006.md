# 인계 — Notify Worker 가 5분 주기로 선언돼 있는데 실제로는 4시간마다 돕니다 (2026-10-06)

**보내는 곳**: ax-sub → bds · **작성**: 2026-10-06
**요청 2건**: ① Notify Worker 발화 주기 ② 월간 AI 해설 수동 1회 검증

## 0. 한 줄

**감시견이 오늘 `Notify Worker 중단 의심`을 🔴로 올렸는데, 실측해 보니 중단이 아니라
처음부터 그렇게 돌고 있었습니다.** 선언은 5분, 실제는 **중앙값 4시간**입니다.
카카오 채널 가격 알림이 그 지연을 그대로 받습니다.

## 2. 그래서 감시견의 🔴 는 오경보입니다 — 그런데 더 나쁩니다

`data_sources.notify-worker` 의 `expected_freshness_hours = 3` 입니다.
실측 간격 99개 중 **70개(71%)가 3시간을 넘습니다.**

> **즉 이 🔴 는 앞으로도 열흘 중 일곱 번 켜집니다.**
> 사람은 그걸 금방 무시하게 되고, **그때 진짜 중단이 와도 똑같이 생겨서 안 보입니다.**

이쪽(ax-sub) 원칙 5는 "조용한 실패를 만들지 않는다"인데, **매번 켜지는 경보도 같은 결과**를 냅니다.
그래서 이 건은 "문턱을 올려서 끄면 끝"이 **아닙니다.** 아래 §4를 봐 주세요.

## 3. 10-05 19:44Z 1건 — 별건입니다

| | |
|---|---|
| run 결론 | `failure` |
| **job 결론** | `cancelled` (19:44:45 → 19:59:46, **15분 01초**) |
| `timeout-minutes` | **4** |
| 실행된 step | **0개** (`steps[]` 가 비어 있음) |

**step 이 하나도 안 돈 채 15분 뒤 취소**됐습니다. `timeout-minutes: 4`는 잡이 *시작된 뒤*부터 재므로,
이건 **큐에서 대기하다 GitHub 쪽에서 취소된 것**으로 보입니다 — 코드 문제가 아니라
§1의 2% 발화율과 같은 뿌리(과밀 스케줄 스로틀링)일 가능성이 큽니다.

> 감시견이 `cancelled · 15분`이라고 적은 것은 **잡 단위 기준으로 정확**했습니다.
> 다만 거기서 "러너 정지/타임아웃 의심 → 중단"으로 간 결론이 §1 때문에 틀렸습니다.

## 4. 요청 A — 두 가지를 **같이** 해 주세요

### A-1. 문턱을 실측에 맞춘다 (경보를 조용하게)

`data_sources.notify-worker.expected_freshness_hours` : **3 → 9**
(실측 최대 8.27시간 + 여유. 9시간을 넘으면 그때는 진짜 이상입니다.)

### A-2. **그런데 A-1만 하면 안 됩니다**

A-1만 하면 **"4시간 지연"이라는 사실이 어디에도 안 남고 경보만 사라집니다.**
그게 이 프로젝트가 제일 경계하는 모양입니다 — 초록불인데 실제로는 안 되고 있는 상태요.

그래서 **발화 방식 자체**를 손봐 주시길 요청합니다. 선택지:

| | 방법 | 비고 |
|---|---|---|
| (a) | Vercel Cron 으로 이관 | 이미 `/api/worker/notify` 가 HTTP 엔드포인트라 옮기기 쉽습니다. **Hobby 플랜 크론 개수 한도**를 먼저 확인해 주세요 |
| (b) | 외부 스케줄러가 엔드포인트를 직접 POST | `CRON_SECRET` 헤더 그대로. GitHub 의존이 사라집니다 |
| (c) | 현상 유지 + 지연을 명시 | 가격 알림이 **최대 8시간 늦게** 갈 수 있다는 것을 제품 사양으로 받아들이는 경우에만 |

**권고는 (a) 또는 (b)입니다.** 이쪽에서 ADR-028로 배운 것이 그대로 적용됩니다 —
*"클라우드로 옮기는 것만으로는 부족하고 **무엇이 깨우느냐**가 같이 중요하다."*
GitHub Actions 스케줄은 이 리포에서 2시간 주기 29%, `collect-gmail` 36%, 그리고 이번 5분 주기 **2%** 로
세 번 연속 같은 성질을 보였습니다. **짧게 선언할수록 더 많이 흘립니다.**

(c)를 고르신다면 그건 그것대로 괜찮습니다 — **다만 그 결정을 적어 주세요.** 적히지 않으면
다음 사람이 똑같이 🔴 를 보고 똑같이 조사합니다.

## 5. 요청 B — 월간 AI 해설, 수동 1회 돌려 주세요

### 지금 상태

```
수정 커밋  4fd8e5f (TPD 즉시 중단 + 창원 우선 정렬 + runstat)   → main 포함
           9ac54b1 (data_sources 행 + markCronStatus 호출)      → main 포함
마지막 실행 2026-10-01T23:44Z  sha=8469bc2  (= 수정 이전)
```

**수정본으로는 한 번도 돈 적이 없습니다.** 다음 정기 발화는 `cron: '0 20 1 * *'` 로 **11-01** 입니다.

### 왜 11-01 을 기다리면 안 되나

이 프로젝트가 같은 걸로 두 번 데였습니다.

1. **수동 성공은 스케줄 성공의 증거가 아니다** — ADR-027 (수동은 되는데 스케줄이 29% 만 발화)
2. **코드 수정은 완주의 증거가 아니다** — 지금이 그 자리입니다

11-01 에 돌려 보고 안 되면 **그 다음 기회는 12-01** 입니다. 한 번 어긋나면 두 달이 날아갑니다.

### 부탁

`workflow_dispatch` 가 열려 있습니다. **1회 수동 실행 후 결과만 알려 주세요.**

확인하고 싶은 것 3가지입니다.

| | 기대값 |
|---|---|
| ① 창원 우선 정렬 | 창원 5구 **5,051행이 먼저** 처리되고 **100% 덮인다** |
| ② TPD 소진 시 깨끗한 중단 | `TpdExhaustedError` 로 **즉시 탈출**, 42분 안팎에 종료 (기존 120분 타임아웃 아님) |
| ③ `markCronStatus` | `data_sources.monthly-commentary` 가 **null 에서 벗어나** `partial` + `reason=groq_tpd_exhausted` 로 기록 |

**예상 결과는 "성공"이 아니라 `status=partial` 입니다.** Groq 무료 200K TPD 로는 전체 2,059 중
일부만 덮는 것이 정상입니다. **창원이 100% 면 통과**입니다.

> ⚠️ **TPD 를 하루치 다 씁니다.** 그날 Groq 를 쓰는 다른 배치가 있으면 피해서 잡아 주세요.
