## 1. 🔴 P0 — 지금 고장 중: 확정 지번이 3일째 갱신되지 않는다

```
ERROR:  permission denied for function refresh_complex_canonical_jibun
```

`Refresh Complex Price Stats` 워크플로가 **08-21·22·23 3연속 실패**했다. 마지막 성공은
08-21T05:19(수동). `complex_canonical_jibun.computed_at` 이 **전 행 2026-08-21T07:56** 로
멈춰 있다.

**원인**: `20260821090000` 이 `refresh_complex_canonical_jibun()` 을 만들면서 **GRANT 를
빠뜨렸다.** 형제 함수는 받았다 —
`20260806040000:97  GRANT EXECUTE ON FUNCTION public.refresh_complex_price_stats() TO service_role, backup_agent;`
`20260821*` 마이그레이션 5개 **어디에도 GRANT 문이 없다**(grep 확인).

**영향**
- 지번 게이트가 **3일 낡은 확정 지번**으로 동작 중 — 그 사이 적재된 거래는 낡은 근거로 붙었다
- 워크플로가 `exit 1` 이라 `data_sources.price-stats` 가 `failed` 로 기록된다.
  **그런데 `refresh_complex_price_stats()` 자체는 성공했다**(로그에 `(1 row)` 확인) —
  즉 감시 지표가 실제와 어긋나 있다. 가격 파생값은 최신, 상태는 빨간불
- 선례가 있다: `20260819060000_restore_function_grants_lost_in_migration.sql`

**조치**: GRANT 마이그레이션 1개. `npm run db:push` 정상 경로.
**검증**: 🔴 `db push` 성공은 검증이 아니다 — 워크플로를 `workflow_dispatch` 로 돌려
exit 0 과 `computed_at` 갱신을 확인한다.

> **재발 방지 후보**: `refresh-price-stats.yml` 이 두 함수를 한 `psql` 호출에 이어 붙여
> 앞이 성공해도 뒤가 죽으면 전체가 실패로 뒤집힌다. 스텝을 쪼개면 어느 쪽이 죽었는지
> 상태에 정확히 반영된다.

## 2. P1 — 최대 레버리지: 운영권역 거래 지번 백필

### 실측 근거

| 적재 시점 | 거래 | jibun 결측 |
|---|---|---|
| ~2026-06 | 296,021 | **58,254 (19.7%)** |
| 2026-07 | 3,202 | 184 (5.7%) |
| 2026-08-01~19 | 1,749 | 63 (3.6%) |
| 2026-08-20~ | 38,323 | **38 (0.1%)** |

부산은 전체 812,881건 중 결측 610건(**0.1%**) — 2026-08-19 재수집으로 들어온 신규
파이프라인이라 깨끗하다. **결측은 옛 적재분의 문제이고 MOLIT 원본에는 지번이 있다**
(`src/services/molit.ts` 스키마에 `jibun` 존재).

### 왜 이게 가장 값이 큰가

게이트 미보호 471곳(운영권역)의 성격을 분해했다:

| 원인 | 곳 |
|---|---|
| 거래는 있으나 지번 5건 미만 → 확정 불가 | **379 (80%)** |
| 거래 0건 | 61 |
| 지번 5건↑인데 다수비율 0.6 미달(쪼개짐) | 31 |

**80%가 재료 부족이다.** 지번을 채우면 게이트 보호율이 **75.1% → 최대 ~95%** 로 오르고,
그러면 오연결이 **애초에 재발하지 않는다.** A(전건 오연결 6,715건)를 손으로 옮기는 것보다
근본적이다.

### 경로가 열려 있는가 — 확인함

`upsertTransaction` 이 `onConflict: 'dedupe_key', ignoreDuplicates: false` 다.
**기존 행을 갱신한다** — 재수집하면 빈 `jibun` 이 채워진다.

⚠️ **다만 재수집은 `lookupComplexIdCached` 를 다시 타므로 `complex_id` 도 다시 붙는다.**
현재 게이트로 재연결되는 것이라 대체로 개선이지만, **A 의 판정이 재수집 전후로 달라진다.**
그래서 순서가 중요하다(§5).

⚠️ **MOLIT 대량 백필은 로컬 병렬이 정답** — GitHub Actions IP 가 data.go.kr 에 차단된다
(회당 ~1/3). 선례: `scripts/busan-backfill-local.sh`, `scripts/core-gap-backfill.sh`.

## 3. P2 — 오늘 감사에서 나온 결함

### A. 전건 오연결 — 94곳 / 6,715건

거래가 통째로 남의 단지에 붙었다. 상세·이동 목표는 `wholesale-mislink-20260824.md`.
상위 9곳 중 5곳이 **이동 목표 없음**(그 지번의 단지가 미등록) — 끊기/신규등록/별칭 중
건마다 판단이 다르다.

🔴 **끊기는 카카오 거리 검증 목록만.** 다필지 단지 2,735건이 걸려 있다.

### B. 단지 주소 오류 — 37곳 (P2 계열)

거래는 맞고 단지의 등록 주소가 엉뚱하다. `센트럴시티`[창원]→`서울 서초구 반포동`,
`삼성아파트1단지`[진해]→`경기 고양시`.

🔴 **두 독립 방법이 수렴했다** — 내 좌표 클러스터 판별 37곳 중 **32곳이 핸드오프 P2
(카카오 역지오코딩) 66곳과 일치**(86%). 반대로 `거래_오연결` 94곳 중 P2 겹침은 **1곳**뿐이다.
판별기가 두 결함을 실제로 갈랐다는 실측 증거다.

P2 66곳 중 29곳은 내 감사가 못 봤다 — 확정 지번이 없는 단지는 대조 자체가 안 된다.
**P1(지번 백필) 이후 재실행하면 이 29곳도 사정권에 들어온다.**

## 5. 실행 순서 — 의존성이 있다

```
P0  GRANT 수정                     ← 이걸 안 하면 아래 전부가 낡은 근거 위에서 돈다
     ↓
P1  운영권역 거래 지번 백필(재수집)   ← complex_id 재연결이 동반된다
     ↓
    확정 지번 재계산 + 게이트 보호율 재측정 (75.1% → ?)
     ↓
P2  A 재측정  ← 재수집이 일부를 자동으로 고쳤거나 바꿨다. **백필 전 판정을 재사용하면 안 된다**
     ↓
    카카오 검증 → 이동/끊기
     ↓
P3  개별 건 (병합·재건축·sgg_code·좌표)
```

🔴 **`wholesale-mislink-20260824.json` 의 94곳 판정은 백필 전 스냅숏이다.** P1 이후
반드시 재실행한다. 그러지 않으면 이미 고쳐진 것을 다시 옮긴다.

### 측정 원칙 (실패 사례에서 나온 것)

- **PostgREST 1,000행 캡** — 이 조사 중 실제로 걸렸다. 게이트 보호율을 22.6% 로
  잘못 쟀다가 페이징을 고쳐 75.1% 로 정정했다. 카운트는 `count:'exact'` 또는 전량 페이징
- **부산 연결률은 합산으로 보지 말 것** — 52.7% 는 기준선(52.8%)과 일치하는 정상값이다.
  연립/다세대 구조적 미매칭 때문이며 아파트만 보면 67.2%
- **충돌 감소는 정확성의 증거가 아니다** — 잘못 옮겨도 충돌은 준다
- **무결성 3축 기준선을 작업 중에 낮추지 않는다** — 현재 7/33/61, 래칫은 개선 방향으로만
