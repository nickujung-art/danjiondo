## 📋 1. `bds`에 직접 넣은 변경 — **미커밋**, 검토 요청

`ax-sub` 세션에서 아래 4개 파일을 고쳤고 **커밋하지 않았다.** 검토 후 처리해 주기 바란다.

| 파일 | 변경 |
|---|---|
| `.github/workflows/compute-predictions.yml` | `schedule:` 주석 처리 + 이름에 `은퇴, 수동 전용` + 근거 주석 |
| `scripts/check-data-freshness.ts` | `columnFilter` 추가 · `AI 가격예측 (Chronos)`로 출처 고정 · 라벨/job 정정 |

| `docs/ARCHITECTURE.md` | `compute-predictions.ts`/`-ai.py` 설명 정정 |

**은퇴 근거 — 앱이 실제로 읽는 2일 창에서 실측(2026-10-01)**

`src/lib/data/invest.ts`는 `MODEL_PRIORITY`(`chronos > holt-winters > double-exp > linear`)로
단지별 최상위 모델만 남기고 나머지 행을 버린다. 읽기 범위는 `computed_at >= 2일 전`.

```
창 안 단지 3,318개 — 고전만 0 / Chronos만 1,735 / 둘다 1,583
=> 고전 모델이 유일한 예측원인 단지: 0개   (7일 창으로 넓혀도 0개)
```

**고전 배치의 산출물은 읽기 시점에 전량 폐기되고 있었다.** 매일 30분을 써서 아무도 읽지 않는
행을 만들고, 그러다 09-27~09-30 나흘 연속 30분 타임아웃으로 중단됐다. 타임아웃 상향은
버려지는 계산에 시간을 더 쓰는 것뿐이다.

**검증한 것**: YAML 파싱 OK(트리거 1개 — `workflow_dispatch`) · 신선도 점검 실행 OK ·
`tsc --noEmit` 통과 · 필터가 두 출처를 독립 판정하는 것을 임시 사본으로 확인.
`npm run test`는 20건 실패하나 **전부 기존 실패**다(아래 4번과 별개 — `src/__tests__/` DB 연동 테스트,
변경을 stash해도 동일).

**되살릴 때**: ① `schedule:` 주석 해제 ② `timeout-minutes`를 30 초과로 ③ `check-data-freshness.ts`의
주석 처리된 `가격예측 (고전 모델)` 줄 복구. 단 **2일 창에서 고전 단독 단지가 0개가 아닌지 먼저 재는 것**이 선행 조건.

## 🔴 2. 커밋 안 된 마이그레이션이 있다 — 프로덕션엔 적용됐는데 리포엔 없다

```
supabase/migrations/20260929000000_idx_unlinked_transactions_sgg_id.sql   (untracked)
```

파일 주석이 스스로 이렇게 적고 있다 — *"CONCURRENTLY로 이미 적용 후 repair 처리"*.

`CLAUDE.md`가 **CRITICAL**로 적어 둔 것과 겹친다 — *"`CREATE INDEX CONCURRENTLY`는 `npm run db:push`로
적용 불가하다"*. 즉 이 인덱스는 수동으로 들어갔고, **파일이 커밋되지 않으면 `db:reset` 한 환경에는
이 인덱스가 없다.** `complex_integrity_counts`가 *"프로덕션 전용 함수, 마이그레이션 drift"*로
남았던 것과 같은 모양이다(ADR Phase 41 기록).

**필요한 판단**: 커밋할 것인가(그렇다면 CONCURRENTLY라 `db:push`로는 안 먹는다는 주석을 함께),
아니면 의도적으로 리포 밖에 두는 것인가. 후자라면 **어디에 그렇게 적혀 있는지**가 필요하다.

같은 상태의 untracked 항목이 둘 더 있다 — 로그류로 보여 판단을 넘긴다:
`.planning/link-tx-logs/` · `.planning/phases/07-data-pipeline/unmatched-log.jsonl`

## 🟡 4. `typecheck:scripts` 래칫이 기준선을 넘은 채로 main에 있다 — CI에는 안 잡힌다

```
scripts/ 타입 오류 7건 / 1개 파일  (기준선 0)
  scripts/backfill-jibun-address.ts(73,60) 외 6곳: error TS18048: 't' is possibly 'undefined'.
```

`5f311ed`("fix: kapt-enrich jibun_address 누락 수정 + 부산 백필 스크립트")에서 들어왔다.

**CI가 못 잡는 이유**: `tsconfig.json`의 `exclude`에 `scripts`가 있어 `npm run lint`(= `next lint && tsc --noEmit`)가
`scripts/`를 안 본다. 래칫은 `tsconfig.scripts.json`을 쓰는 **별도 명령**이고 **CI 워크플로에 없다.**
래칫 파일 머리말이 그 이유를 이미 적어 뒀다.

→ 그래서 **조용히 빨강**이다. 오늘 제가 `check-data-freshness.ts`를 고치고 래칫을 돌렸을 때
제 변경 때문인 줄 알고 멈췄다(stash해서 기존 실패임을 확인했다). **다음 사람도 같은 데서 멈춘다.**

**선택지**: ① `backfill-jibun-address.ts` 7건을 고쳐 기준선 0으로 되돌린다 ②
래칫을 CI에 넣어 조용한 빨강을 없앤다 ③ 기준선을 7로 올리고 그 이유를 적는다.
①+②가 래칫의 원래 의도에 맞지만 판단은 넘긴다.

## 📋 5. 제안 — 새 배치를 기존 테이블에 붙일 때

`complex_price_predictions`에 두 배치가 쓰면서 **하나가 죽어도 다른 하나가 초록불을 만들어 줬다.**
나흘 동안 `AI 가격예측 0.2일` 초록이었다.

이 저장소에서 **같은 구멍이 세 번째**다:

| 시점 | 테이블 | 가린 쪽 | 막은 수단 |
|---|---|---|---|
| 2026-08-04 | `transactions` | 오피스텔 배치가 아파트 전멸을 가림 | `embeddedFilter` (`source_run_id` 조인) |
| 2026-08-04 | `transactions` | `building_type`으로는 못 걸러짐 | 위와 같음 |
| **2026-10-01** | `complex_price_predictions` | Chronos가 고전 배치 전멸을 가림 | `columnFilter` (`model_name`) |

**규칙 제안**: 기존 테이블에 쓰는 배치를 새로 만들 때 `check-data-freshness.ts`의 해당 점검에
**출처 필터를 같이 넣는다.** 안 넣으면 그 점검은 두 배치 중 더 부지런한 쪽만 본다.

참고로 `월간 AI 해설`(`ai_cached_at`) 점검에는 필터를 넣지 않았다 — 그 컬럼에 쓰는 배치가
하나뿐이라 가면이 생기지 않는다. 확인 없이 넣으면 "데이터 없음" 오탐이 난다.

> ## 🟡 2. 데이터 신선도 점검 — 10-01 자동 해결 예상
> **월간 크론이라** 10-01 실행에서 풀릴 것. 10-01 이후에도 빨강이면 별도 원인 추적.

두 군데가 사실과 다르다.

| 적힌 것 | 실제 |
|---|---|
| 신선도 점검이 **월간 크론** | **매일 크론**이다 — `data-freshness-check.yml`의 `cron: '0 23 * * *'` |
| 10-01 실행에서 풀린다 | 신선도 점검은 09-24~10-01 **매일 돌고 매일 실패**했다(실측 8회 연속 확인). 풀릴 대상은 신선도 점검이 아니라 **월간 AI 해설**이고, 그 크론은 `0 20 1 * *` = **10-02 05:00 KST** |

원인 진단(**qwen 교체가 필요했다**)은 맞았고 **날짜와 주체만 어긋났다.** 위 3번이 그 검증이다.

덤으로 측정된 것: 신선도 점검은 23:00Z 크론인데 실제 발화가 **01:11Z~02:30Z**로 8일 내내
**2~3.5시간 지연**됐다. ADR-027의 Actions 스케줄 지연이 일일 크론에서도 관측된다 —
조치 대상은 아니고 기록만 남긴다.
