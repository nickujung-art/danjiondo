## 문제 정의

### 문제 1 — 크론 상태 보고가 조용히 실패한다

`src/lib/data/cron-status.ts`의 세 함수가 `.update()`의 error를 확인하지 않는다.

```ts
export async function markCronSuccess(supabase, sourceId) {
  await supabase.from('data_sources').update({...}).eq('id', sourceId)
  //    ^ error 미확인. 0행 갱신도 에러가 아니다
}
```

호출부는 한술 더 뜬다:

```ts
// daily/route.ts
await markCronStatus(supabase, 'kapt', ...)
  .catch(() => {/* kapt source 미등록이면 무시 */})
```

주석의 전제도 **틀렸다** — `data_sources`에 `kapt` 행은 등록돼 있다(실측 확인).

**결과**: `data_sources.kapt`가 `last_synced_at: null` / `last_status: null`인데
아무도 모른다. 크론이 고장나도 조용하다.

이건 다른 세션이 오늘 고친 `increment_view_count` 버그와 **같은 클래스**다 —
RLS/조건 불일치로 0행 UPDATE가 에러 없이 "성공"한다.

### 문제 2 — K-apt 일배치가 매일 같은 50개만 처리한다

```ts
const { data: complexesWithKaptCode } = await supabase
  .from('complexes').select('id, kapt_code')
  .not('kapt_code', 'is', null)
  .limit(50)          // offset·정렬·순환 없음
```

**실측 규모**:

| | |
|---|---|
| `kapt_code` 보유 단지 | **2,922** |
| 그중 `facility_kapt` 행 없음 | **1,463 (50%)** |

정렬이 없어 순서가 비결정적이고, offset이 없어 **나머지 단지는 영원히 수집되지 않는다.**

## 해결 접근법

### 설계 판단 — throw가 아니라 결과 반환

`cron-status.ts`를 **throw하도록** 바꾸면, 현재 `.catch()` 없이 호출하는
`rankings`·`cafe-ingest`·`notify` 3개 라우트가 **지금까지 조용히 지나가던 지점에서
500을 내기 시작한다.** 크론을 고치려다 크론을 죽이는 셈이다.

→ **`Promise<boolean>`을 반환하고 실패 시 `console.error`로 로그를 남긴다.**
- 기존 3개 라우트: 반환값을 무시하므로 **동작 불변**. 다만 이제 Vercel 로그에 실패가 남는다
- `daily/route.ts`: 반환값을 확인해 `errors[]`에 넣는다 → JSON 응답과
  `daily-batch` `partial` 상태로 드러난다

파일 5개(GSD 트리거) → 2개(FIX LOOP)로 줄이는 효과도 있다.

### 문제 1 수정

**`cron-status.ts`** — 세 함수 모두:
- `.update(...).eq('id', sourceId)` 뒤에 **`.select('id')`** 를 붙여 갱신된 행을 받는다
- `error`가 있으면 `console.error` 후 `false` 반환
- `data`가 비어 있으면(= 해당 `id` 없음) 그 사실을 명시해 `console.error` 후 `false` 반환
- 정상이면 `true` 반환
- `markCronStatus`는 세 함수의 반환값을 그대로 전달

**`daily/route.ts`** — 침묵 catch 5곳 제거:
```
kapt / molit_offi_trade / gap-stats(실패) / gap-stats(성공) / gap-stats(catch)
```
각각 반환값이 `false`면 `errors.push(...)`.

⚠️ 마지막 `markCronStatus(supabase, 'daily-batch', ...)`는 `errors` 배열을 읽어
상태를 정하므로 **그 호출보다 앞에서** 모든 push가 끝나야 한다. 현재 코드 순서가
이미 그렇다.

### 문제 2 수정 — code-reviewer HIGH 2건 반영해 재설계

**폐기한 초안**: 일자 기반 offset(`(dayOfYear % ceil(total/BATCH)) * BATCH`).
두 가지 이유로 버린다.
- `total` 산출 방식이 모호하다 (code-reviewer HIGH)
- **시간 컷오프와 상극이다.** 70개 중 40개만 처리해도 다음날 offset은 70만큼
  전진해 **30개가 영구히 건너뛰어진다.** 부분 처리에 취약한 설계다

**채택: 자기교정 우선순위 방식** — `facility_kapt.updated_at`(컬럼 존재 확인됨) 활용

1. `complexes`에서 `kapt_code IS NOT NULL`인 단지 전체를 **페이지네이션**으로 수집 (2,922건 → 3페이지)
2. `facility_kapt`의 `complex_id, updated_at` 전체를 **페이지네이션**으로 수집 (3,661건 → 4페이지)
3. 클라이언트에서 정렬: **`facility_kapt` 없음 우선 → 그다음 `updated_at` 오래된 순**
4. 앞에서 `KAPT_BATCH_SIZE`개를 취한다

⚠️ **PostgREST 기본 1,000행 캡** 때문에 두 쿼리 모두 `.range()` 페이지네이션이 필수다
(Phase 34에서 이미 겪은 이슈).

**이 방식의 이점**:
- **자기교정**: 처리 못 한 단지는 다음 실행에서 여전히 "가장 오래된" 쪽에 남아 재시도된다.
  부분 배치·실패가 누락으로 이어지지 않는다
- `total` 카운트 쿼리 불필요 (배열 길이로 충분)
- `dayOfYear` 경계조건(연말·윤년·타임존) 없음
- **1,463개 미수집분이 자동으로 최우선**이 되어 backlog가 먼저 해소된다

### 문제 2-b — 타임아웃 리스크 차단 (code-reviewer HIGH)

현재 **K-apt 루프가 라우트의 맨 앞**(라인 33~71)이다. 여기서 타임아웃이 나면
지금 정상 동작 중인 `presale`·`cheongyak`·`offi`·`gap-stats`·`daily-batch`가
**전부 실행되지 않는다.** 배치를 키우면 그 리스크가 커진다 — 고치려다 더 크게 깨뜨리는 셈.

**세 가지를 함께 적용한다**:

1. **K-apt 블록을 라우트 마지막으로 이동** (gap-stats 뒤, 최종 `daily-batch` 마킹 앞).
   K-apt는 SLA 45일짜리 시설 데이터로 **우선순위가 가장 낮은데 맨 앞에서 돌고 있었다.**
   `const activeSggCodes = await getActiveSggCodes(supabase)`(라인 35)는 presale이 쓰므로
   **제자리에 남긴다**
2. **시간 예산 컷오프**: 루프 안에서 경과시간이 `KAPT_TIME_BUDGET_MS`를 넘으면 중단.
   중단 시 처리 건수를 `errors[]`가 아니라 응답 JSON에 남겨 가시화 (부분 처리는 정상 동작이지
   에러가 아니다)
3. **`export const maxDuration` 명시** — 현재 `vercel.json`에도 라우트에도 없어 플랫폼
   기본값에 노출돼 있다

**배치 크기**: `KAPT_BATCH_SIZE = 70` (2,922건 ÷ 70 ≈ 42일 순환, SLA 45일 충족).
시간 예산이 안전망이므로 70이 과해도 크론 전체를 위협하지 않는다.

⚠️ 1,463개 backlog는 위 우선순위 정렬로 **먼저** 채워진다(약 21일). 즉시 해소하려면
`kapt-enrich-once.yml` 수동 1회 실행이 빠르다 (이 FIX 범위 밖, 사용자 판단).
